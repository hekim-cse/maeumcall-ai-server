# MaeumCall AI Server 학습 가이드

이 문서는 구현 결과만 보여주는 대신, 주요 설계 결정을 질문과 답 형식으로 설명합니다.

## Q1. 왜 단순한 LLM 채팅 API가 아니라 LangGraph를 사용했나요?

예약은 `정보 수집 → 확인 → 가능 여부 조회 → 확정 → 종료`처럼 이전 상태에 따라 다음 행동이 달라집니다. 프롬프트 하나에 이 책임을 모두 넣으면 상태 전이가 모델 문장에 묻혀 테스트하기 어렵습니다. LangGraph는 노드가 수행하는 일과 edge가 허용하는 전이를 코드로 분리하므로, 잘못된 순서로 예약이 확정되는 문제를 테스트할 수 있습니다.

```python
builder.add_node("extract_info", extract_info_node)
builder.add_node("decide_state", decide_state_node)
builder.add_conditional_edges("decide_state", route_after_decide)
```

## Q2. 사용자 발화를 왜 JSON으로 변환하나요?

그래프가 자연어 문장을 직접 읽고 분기하면 분기 조건이 문자열 검색에 의존합니다. 대신 모델이 `date`, `time`, `user_action` 같은 계약을 반환하고 서버가 이를 검증하면, 그래프는 타입이 확인된 데이터만 다룹니다.

```python
validate_action_field_delta(
    fields,
    user_action=user_action,
    contract=RESTAURANT_ACTION_FIELD_CONTRACT,
)
```

여기서 `fields`는 지금까지 저장된 전체 예약 정보가 아니라 **이번 사용자 발화에서 새로 읽은 변화량**입니다. 예를 들어 “네, 확정할게요”는 확인 행동만 있고 새 날짜·시간은 모두 `null`이어야 합니다. 반대로 “날짜를 모레로 바꿔주세요”는 `change_date`와 `date=모레`만 함께 올 수 있습니다. JSON 키와 타입 검사가 그릇의 모양을 확인한다면, action-field 교차 계약은 그 안의 행동과 값이 서로 모순되지 않는지 확인합니다.

## Q3. 모델 출력이 잘못되면 왜 기본값으로 계속 진행하지 않나요?

`user_action=unknown` 같은 값을 자동으로 넣고 성공 응답을 반환하면 모델 장애가 정상 대화처럼 보입니다. 날짜나 확정 의도를 잘못 채우는 것은 더 위험합니다. 이 서버는 검증 오류를 포함해 한 번 재요청하고, 두 번째 출력도 잘못되면 타입이 있는 오류를 API 경계까지 전달합니다.

이 제한 재시도와 명시적 실패 경계 자체는 기존부터 16개 구조화 NLU에 공통이었습니다. 이번 보강은 실패 횟수를 바꾼 것이 아니라 검증 범위를 넓힌 작업입니다. 예를 들어 `change_date`가 날짜 외 필드를 함께 반환하거나 확인 행동이 새 예약 정보를 함께 반환하면, JSON 모양이 맞아도 행동과 값이 모순되므로 계약 실패입니다.

예약 대체 시간도 모델이 비슷한 문자열을 임의로 만들 수 없습니다. 서버가 `오후 3시`, `오후 4시`를 제시했다면 `select_alternative_time`은 두 값 중 하나와 정확히 일치해야 합니다. `오 후 4 시`처럼 공백을 바꾼 값도 계약 위반으로 재시도하며, 서버 노드가 이를 다른 행동으로 보정하지 않습니다.

## Q4. 왜 JSON 코드블록을 서버가 알아서 벗기지 않나요?

서버가 모델의 계약 위반을 계속 보정하면 허용 범위가 점점 넓어지고 품질 저하가 지표에 잡히지 않습니다. 출력 계약이 “JSON 객체 하나”라면 markdown이 섞인 결과는 실패입니다. 재시도 프롬프트에 원인을 알려 모델이 계약을 지키게 하고, 반복 실패는 관측 가능한 오류로 남깁니다.

## Q5. 예약 응답은 왜 LLM이 아니라 응답 정책으로 만드나요?

`예약 가능`, `예약 완료`는 창의적으로 생성할 문장이 아니라 서버 상태가 보장해야 하는 사실입니다. 모델은 발화 이해에 사용하고, 확정된 상태를 사용자 문장으로 표현하는 일은 도메인 정책이 담당합니다.

```python
if conversation_state == "reservation_confirmed":
    return f"{date} {time} {department} 진료로 예약 완료됐습니다."
```

이 분리는 모델이 존재하지 않는 시간이나 예약 결과를 만들어내는 것을 구조적으로 막습니다.

## Q6. 자유 대화 시나리오는 어떻게 다르게 처리하나요?

가족·친구·연인처럼 정답 문구가 없는 상황은 모델 생성이 필요합니다. 이때도 자유 문자열만 받지 않고 `action`, `response`, `etiquette_tip`을 하나의 JSON 객체로 검증합니다. 종료 판단과 실제 응답이 같은 모델 결과에 포함되므로 상태와 문장이 일치합니다.

## Q7. 모델을 끈 단위 테스트가 의미 있나요?

의미 있습니다. 단위 테스트의 목적은 모델 품질이 아니라 우리 코드의 상태 전이, 라우팅, 오류 처리를 재현 가능하게 검증하는 것입니다. 모델 경계에는 고정 JSON을 주입하고, 실제 모델 호환성은 별도의 integration test로 검증합니다.

```bash
pytest -q
HF_LOCAL_MODEL_ENABLED=1 pytest -m integration -q
```

## Q8. 왜 미등록 시나리오를 일반 채팅으로 처리하지 않나요?

우회 처리를 허용하면 모바일 제목 변경이나 레지스트리 누락이 배포 후에도 발견되지 않습니다. 미등록 조합은 `422 UNSUPPORTED_SCENARIO`로 실패시켜 클라이언트와 서버 계약 불일치를 바로 드러냅니다.

## Q9. 이 구조를 다음 단계에서 어떻게 확장해야 하나요?

우선순위는 다음과 같습니다.

1. 이미 수집 중인 노드별 latency, 모델 재시도, 계약 검증 실패 지표에 운영 임계값과 대시보드 경보를 연결합니다.
2. 의미 그룹과 초안 case 목록을 만든 뒤, 어떤 모델 결과도 보기 전에 development·validation·test 배정을 별도 원장에 고정합니다.
3. 정답 판정 기준과 검수 이력을 연결한 뒤, 현재 평가 계약과 벤치마크 프로필에 맞춰 16개 상세 그래프의 골든 데이터셋을 작성합니다.
4. 골든 데이터 검토가 끝나면 모델·프롬프트·런타임·Git 리비전과 원시 결과를 함께 고정하는 실행기와 manifest 계약을 구현합니다.
5. 같은 corpus와 manifest 계약 아래에서 `user_action`, 필드 F1, 사실 생성률을 후보 모델별로 비교합니다.
6. 다중 기기 재개나 노드 단위 복구가 제품 요구사항이 되면 영속 checkpointer와 인증된 `thread_id`를 도입하고 API 계약 버전을 올립니다.

새 기능을 추가할 때는 “모델이 판단할 일”, “그래프가 보장할 일”, “도메인 정책이 표현할 일”을 먼저 나누는 것이 핵심입니다.

## Q10. 음성의 pitch, jitter, shimmer로 불안이나 자신감을 판단할 수 있나요?

이 서버에서는 그렇게 판단하지 않습니다. 녹음 환경, 화자 특성, 건강 상태처럼 통제되지 않은 변수가 많으므로 고정 임계값으로 심리 상태를 단정하면 근거 없는 피드백이 됩니다. 서버는 측정값과 사용자 자신의 기준선 대비 변화만 반환합니다. 심리 상태 분류가 필요하다면 별도의 라벨 데이터, 평가 지표, 동의 절차를 갖춘 모델 검증 과제로 분리해야 합니다.

## Q11. 모델과 프롬프트 버전은 왜 함께 고정해야 하나요?

모델 저장소의 기본 브랜치는 같은 모델명 아래에서도 바뀔 수 있습니다. 이 프로젝트의 현재 운영 기준선은 Hugging Face 모델명과 커밋 리비전을 환경 설정에 함께 기록하고, 원격 사용자 코드 실행 없이 표준 Transformers 구현을 사용합니다. 그래야 개발 환경과 CI에서 어떤 가중치와 토크나이저를 대상으로 검증했는지 설명할 수 있습니다.

다만 모든 후보가 이 로딩 방식과 호환되는 것은 아닙니다. 예를 들어 Kanana 2 1.3B 공식 모델 카드는 저장소의 사용자 정의 모델 코드를 실행하는 `trust_remote_code`를 요구합니다. 편의를 위해 바로 허용하면 다운로드한 저장소 코드가 로컬에서 실행되므로, 후보 등록 전에 코드 검토·격리 환경·라이선스·Transformers 버전 호환성을 별도 관문으로 확인해야 합니다. 이 관문을 통과하지 않은 모델은 이름만 후보표에 있다고 해서 실행하지 않습니다.

## Q12. 왜 현재 LangGraph checkpointer를 바로 붙이지 않았나요?

현재 API는 모바일이 직전 `scenarioState`를 저장해 다음 요청에 전달합니다. 여기에 서버 checkpointer까지 추가하면 같은 상태의 원본이 두 개가 되고, 충돌 시 어느 쪽을 선택할지 별도 규칙이 필요합니다. 프로세스 재시작 시 사라지는 메모리 checkpointer는 운영 영속성도 제공하지 못합니다.

그래서 2.1에서는 클라이언트 소유 상태를 `scenario_key`, `state_version`, 필드 allowlist로 엄격하게 검증합니다. 서버 소유 상태가 필요해지는 시점에는 영속 저장소, 인증된 세션 식별자, 보존·삭제 정책을 함께 설계하고 계약 버전을 올립니다.

여기서 엄격한 검증은 상태의 키·버전·필드 조합이 올바른지 확인한다는 뜻이지, 익명 클라이언트가 서버 응답을 한 글자도 바꾸지 않았음을 증명한다는 뜻은 아닙니다. 현재는 외부 시스템에 아무 변화도 만들지 않는 통화 연습 서비스라 이 경계를 허용합니다. 실제 접수 기능을 붙인다면 별도 HMAC을 덧붙이는 것만으로 끝내지 않고, 로그인한 사용자와 서버 소유 세션을 연결해 상태 원본을 서버에 보관해야 합니다. 그래야 만료·재사용·여러 기기 충돌까지 함께 다룰 수 있습니다.

## Q13. 실제 사용자 ID를 파일 키로 저장하면 왜 안 되나요?

기준선 값 자체뿐 아니라 저장 키도 개인을 연결하는 식별 정보가 될 수 있습니다. 서버는 원본 ID를 저장하지 않고, 운영 비밀값을 키로 사용하는 HMAC-SHA256 결과를 저장 키로 사용합니다. 단순 SHA-256은 ID 후보를 대입해 같은 해시를 만들 수 있으므로 충분하지 않습니다. 비밀값이 없으면 임의의 기본값으로 실행하지 않고 `503 VOICE_BASELINE_SECURITY_NOT_CONFIGURED`로 실패합니다.

## Q14. 공백으로 단어를 나누면 왜 한국어 빈도 분석이 부정확한가요?

한국어의 조사와 어미는 앞말에 붙습니다. 예를 들어 `학교에서`와 `학교를`을 공백으로 나누면 서로 다른 단어가 되지만, 형태소 분석 결과에서는 둘 다 `학교/NNG`와 조사로 분리됩니다. 서버는 Kiwi가 반환한 형태소 원형과 품사를 사용해 이 문제를 해결합니다.

내용어는 명사·동사·형용사·부사처럼 코드에 공개한 품사 집합으로 정의하고, 군더더기 표현은 감탄사 품사 `IC`로만 집계합니다. 과거처럼 `그냥`, `좀`, `약간`을 고정 목록에 넣어 문맥과 무관하게 군더더기로 판정하지 않습니다. 한 글자 명사도 의미가 있을 수 있으므로 글자 수 필터도 사용하지 않습니다.

Kiwi가 설치되지 않았거나 분석 중 오류가 나면 공백 분리 결과를 정상 응답처럼 반환하지 않습니다. `/health/ready`의 `korean_text_analyzer`가 준비되지 않은 상태를 알리고 API는 `KOREAN_TEXT_ANALYZER_UNAVAILABLE` 또는 `KOREAN_TEXT_ANALYSIS_FAILED`를 반환합니다. 따라서 운영자는 분석 품질이 바뀐 사실을 즉시 알 수 있습니다.

## Q15. 통화 시작 전에 시나리오를 왜 다시 검증하나요?

모바일 앱과 서버는 같은 시점에 배포된다는 보장이 없습니다. 오래된 앱이 삭제된 시나리오를 보내거나 요청이 직접 조작될 수도 있습니다. `/call/setup`은 중앙 LangGraph 레지스트리에서 `category + title`을 검증하고, 서버가 확정한 `scenario_key`와 버전이 붙은 통화 계획만 반환합니다.

통화 방향 정책도 별도 문자열 조건문으로 추측하지 않습니다. 32개 등록 시나리오 각각이 정확히 하나의 통화 정책을 가지는지 초기화와 테스트에서 비교합니다. 모바일은 같은 시나리오의 준비 요청이 동시에 들어오면 진행 중인 Future를 공유하므로 네트워크 요청을 중복 전송하지 않습니다.

## Q16. 테스트가 통과하는데 정적 분석도 필요한가요?

테스트는 실행된 경로의 결과를 검증하지만, 호출되지 않은 코드의 미정의 이름이나 미사용 import, 파일별 형식 불일치를 모두 찾지는 못합니다. Ruff는 Python 3.11을 기준으로 이러한 문제를 검사하고, 로컬 `make lint`와 GitHub Actions가 같은 명령을 실행합니다.

외부 GitHub Action은 `@v6`처럼 나중에 다른 코드로 이동할 수 있는 태그 대신 검증한 릴리스의 40자리 커밋 SHA로 고정합니다. 버전 주석은 사람이 업데이트 대상을 읽기 위한 정보이고, 실제 실행 코드는 SHA가 결정합니다.

## Q17. 외부 시스템이 없는데 환불 승인이나 A/S 접수 완료를 만들면 안 되나요?

전화 연습 서비스 안의 모의 결과로는 만들 수 있습니다. 문제는 그 결과를 실제 주문·결제·기관 시스템의 처리라고 표현하는 것입니다. 서버는 모든 `/chat` 응답에 `simulation.externalEffect=false`를 넣고, 완료 문장에도 실제 시스템에 반영되지 않았다고 표시합니다.

업무 그래프는 정보가 모였다는 이유만으로 바로 완료하지 않습니다. 사용자가 내용을 확인하면 `ready`, 다시 모의 처리를 진행해 달라고 명시하면 `completed`로 전이합니다. 이 두 단계를 분리하면 “정보 확인”과 “행동 승인”을 각각 테스트할 수 있습니다.

## Q18. 무료 TTS 중 Qwen3-TTS를 선택한 이유는 무엇인가요?

Apache-2.0 라이선스, 한국어 지원, 9개 고정 음색, 로컬 실행, 공식 Python 패키지를 함께 충족했기 때문입니다. 모델명만 쓰면 나중에 가중치가 바뀔 수 있으므로 Hugging Face 커밋 SHA까지 고정했습니다. 비공식 웹 서비스를 대신 호출하는 방식은 서비스 약관과 가용성을 통제할 수 없어 사용하지 않았습니다.

0.6B 모델은 2.5GB 규모로 이 컴퓨터의 Apple MPS에서 실제 24kHz 한국어 WAV 생성까지 검증했습니다. 다만 공식 기능 표에서 0.6B의 세밀한 지시 제어는 보장되지 않으므로, `차분함`, `친절함` 같은 말투를 코드가 임의로 확정하지 않습니다.

## Q19. 왜 TTS 모델을 `/chat` 안에서 바로 호출하지 않나요?

텍스트 응답과 음성 합성은 실패 원인과 처리 시간이 다릅니다. `/chat`이 성공한 뒤 `/tts/scenario/synthesize`를 호출하면, 음성 장치나 모델 메모리 문제가 대화 상태 전이를 되돌리지 않습니다. TTS 공급자 인터페이스를 두었기 때문에 모델을 교체해도 인증·요청 검증·WAV 응답 계약은 유지할 수 있습니다.

합성 API는 계산량이 크므로 Firebase 인증을 요구합니다. 서버가 꺼진 기능이나 모델 장애를 다른 음성으로 몰래 대체하지 않고 `TTS_*` 오류로 반환하는 것도 같은 이유입니다.

## Q20. TTS, MPS, WAV, 모델 리비전은 각각 무엇인가요?

- **TTS(Text-to-Speech)**: 글자를 사람이 말하는 음성 신호로 바꾸는 기술입니다.
- **MPS(Metal Performance Shaders)**: Apple Silicon의 GPU를 PyTorch 계산에 사용하는 실행 장치입니다.
- **WAV**: 압축 손실 없이 PCM 음성 샘플을 담을 수 있는 파일 형식입니다. 현재 계약은 24kHz·16비트·모노 WAV입니다.
- **모델 리비전**: Hugging Face 저장소의 특정 커밋 SHA입니다. 같은 모델 이름 아래 파일이 바뀌어도 이 값으로 검증한 버전을 다시 찾을 수 있습니다.

## Q21. 왜 모바일이 음성 이름을 직접 보내지 않나요?

모바일이 `ryan`이나 `ko_speaker_5`를 저장하면 배역 정책이 앱과 서버 양쪽에 중복됩니다. 이후 음성을 바꿀 때 구버전 앱은 계속 예전 값을 보내므로 운영 결과가 갈라집니다. 모바일은 `/chat`이 반환한 `scenarioKey`, 명시한 `castVersion`, 가족 역할만 보내고 서버가 승인 배역을 결정합니다.

`castVersion`은 배역표의 의미를 고정하는 번호입니다. 기존 버전을 조용히 수정하지 않기 때문에 어떤 앱 요청이 어떤 목소리로 합성됐는지 헤더와 로그에서 추적할 수 있습니다.

## Q22. 왜 시나리오별 목소리를 바로 지정하지 않았나요?

음색 설명은 제작자의 일반 설명일 뿐, 한국어 전화 상황에서 자연스럽다는 검증 결과가 아닙니다. 같은 문장을 9개 음색으로 합성해 문장 차이를 제거하고 사람이 직접 들은 뒤 역할과 상황을 정해야 합니다. 특히 비한국어 원어민 음색은 한국어 발음이나 종료 타이밍이 달라질 수 있으므로, 코드의 추측으로 배정하지 않습니다.

## Q23. 모델 평가의 coverage, split, macro, micro, adjudicated는 무엇인가요?

시험에 비유하면 이해하기 쉽습니다.

- **coverage(평가 범위 충족도)**: 점수가 아니라 시험 범위표입니다. 예약·교수님 같은 시나리오, 대화 상태, 확인·수정·취소 같은 행동, 날짜·시간 같은 필드가 시험지에 빠지지 않았는지 확인합니다. 쉬운 문제만 넣고 100점을 받는 일을 막습니다.
- **split(데이터 분할)**: 문제를 사용하는 시점을 나누는 것입니다. `development`는 문제와 코드를 만들며 연습하는 묶음, `validation`은 후보 설정을 고르는 모의고사, `test`는 최종 비교 전까지 보지 않는 시험지입니다. 같은 문장을 조금 바꾼 문제가 다른 split으로 새면 이미 본 문제를 푸는 것과 같으므로 같은 대화에서 나온 사례는 한 묶음에 둡니다.
- **adjudicated(정답 확정)**: 초안 작성과 검토 뒤에 오류나 의견 충돌을 해결해 정답을 확정한 상태입니다. 단어 자체가 특정 검토 횟수를 뜻하지는 않습니다. 현재 코드는 최종 상태를 저장하고, 누가 무엇을 고쳤는지는 Git 커밋과 PR 리뷰에서 추적합니다.
- **macro 평균**: 행동 종류마다 점수를 먼저 구한 뒤 같은 비중으로 평균냅니다. `정보 제공`이 100건이고 `취소`가 2건이어도 두 행동을 같은 비중으로 보므로 드문 행동의 실패를 숨기기 어렵습니다.
- **micro 집계**: 모든 판정을 한 바구니에 모아 합계를 계산합니다. 현재 필드 존재 precision·recall·F1은 모든 필드의 TP·FP·FN을 합친 slot-micro 방식입니다.

여기서 **TP(True Positive)**는 값이 있어야 하는 필드를 모델도 있다고 맞힌 경우, **FP(False Positive)**는 정답이 비어 있는데 값을 만들어낸 경우, **FN(False Negative)**은 정답 값이 있는데 모델이 놓친 경우입니다.

예를 들어 정답이 `날짜=내일`, `시간=null`인데 모델이 `날짜=내일`, `시간=오후 3시`를 반환했다면 날짜는 TP이고 시간은 FP입니다. 필드 존재 F1이 좋다는 것은 “어느 칸을 채울지”를 잘 맞힌다는 뜻이지, 채운 문자열 자체가 정확하다는 뜻은 아닙니다. 그래서 마음콜은 필드 값 정확 일치율도 별도로 계산합니다.

마음콜 프로젝트 내부 공식 벤치마크 결과가 되려면 고정된 프로필의 coverage를 통과하고, `test` split의 모든 케이스가 `adjudicated`여야 하며, 데이터·모델·프롬프트·런타임(실행 환경)·Git 리비전과 실행 결과를 함께 보존해야 합니다. 현재는 coverage, test split, adjudicated 상태와 프로필 지문(내용 식별값)을 강제하는 검사기까지 구현했으며, 실제 골든 데이터·실행 조건 기록 파일·후보 모델 점수는 아직 작성·산출하지 않았습니다.

`conversation_group_id`는 같은 원본 대화에서 파생된 문장에 붙이는 묶음 번호입니다. 예를 들어 “내일 예약할게요”와 “내일로 예약 부탁해요”가 같은 원본을 바꿔 쓴 문장이라면 같은 그룹 ID를 사용합니다. 코드는 한 그룹이 development와 test에 동시에 들어가는 것을 거부하므로, 연습 중 본 표현이 최종 시험 점수를 부풀리는 일을 막습니다.

여기서 **corpus(코퍼스)**는 세 split을 모두 담은 평가 문장 전체 묶음이고, **test slice**는 그중 최종 시험에 쓰는 test 사례만 꺼낸 묶음입니다. test 파일만 따로 받으면 같은 원본 문장이 development나 validation에 있는지 확인할 수 없습니다. 그래서 공식 결과 후보 관문은 완전한 corpus를 요구하고, 전체 내용 식별값을 확인한 뒤 test slice를 다시 꺼냅니다.

상태-행동 조합은 상태와 행동을 따로 세는 것이 아니라 실제로 허용된 짝을 확인한다는 뜻입니다. 예를 들어 `확인 중` 상태와 `취소` 행동이 각각 다른 문제에 한 번씩 등장한 것만으로는 부족하고, `확인 중 → 취소` 경로 자체도 시험해야 합니다. 배달·시청·고객센터의 공통 workflow 기반 상세 그래프에서는 여기에 현재 값까지 검사합니다. 예를 들어 확인 단계라면 필수 값이 모두 있어야 하고, 주문 변경 유형처럼 선택지가 정해진 값은 허용 목록 안에 있어야 합니다.

행동과 필드도 짝으로 검사합니다. `change_date` 행동과 `date` 필드가 서로 다른 문제에 한 번씩 등장하는 것만으로는 같은 문장에서 새 날짜를 올바르게 추출하는 능력을 검증할 수 없습니다. 그래서 V2 프로필은 `change_date + date 있음`과, 새 값을 아직 말하지 않은 변경 행동을 지원한다면 `change_date + date 없음`도 각각 시험 범위로 요구합니다.

모델 답만으로 계약을 판단할 수 없는 경우에는 서버 문맥도 골든 케이스에 보존합니다. 9개 업무 workflow의 `current_fields`는 이전 턴까지 모은 값이고, 예약 4개의 `offered_alternative_times`는 서버가 이번 턴에 실제로 제시한 후보 목록입니다. 대안 시간 목록은 모델이 만든 정답이 아니라, 모델의 선택값이 서버가 제시한 값과 정확히 같은지 확인하는 기준입니다.

## Q24. 골든 데이터는 어떻게 작성하고 검수하나요?

**annotation(어노테이션)**은 사용자 문장에 정답 표시를 붙이는 작업이고,
**label(라벨)**은 그 정답 값입니다. 예를 들어 “내일 오후 세 시로 예약해 주세요”에
`date=내일`, `time=오후 세 시`, `user_action=정보 제공`을 기록하는 것이
annotation입니다. 어떤 표현을 어떤 값으로 판정할지 정한 규칙을 annotation
guideline 또는 rubric이라고 합니다.

골든 데이터의 `golden`은 문장이 자동으로 참이 된다는 뜻이 아닙니다. 초안을
작성하고, 라이브 서비스 계약과 대조하고, 모호한 판단을 다시 검토해 기준 답안으로
승인했다는 뜻입니다. 그래서 상태를 다음처럼 구분합니다.

- `draft`: 정답을 처음 작성한 상태
- `reviewed`: 다른 시점의 검토에서 형식과 의미를 확인한 상태
- `adjudicated`: 의견 차이나 오류를 해결해 최종 답으로 확정한 상태

한 `case`는 모델 호출 한 번에 들어가는 상태·문장·정답 묶음입니다. `turn`은
대화 한 번의 발화 단위이고, `conversation_group_id`는 같은 의미 원본에서 파생한
표현들을 묶는 번호입니다. “내일 예약할게요”와 “내일로 잡아 주세요”가 같은
원본을 바꿔 쓴 문장이라면 같은 그룹에 두고 모두 같은 split을 사용합니다.

`null`은 해당 키를 빼먹었다는 뜻이 아니라 “이번 발화에서는 이 필드의 값이
없다”는 명시적인 정답입니다. 키 자체가 없으면 JSON 계약 위반이고, 키는 있지만
값이 `null`이면 모델이 비어 있음을 올바르게 판단했는지 평가할 수 있습니다.

`accepted_values`는 비슷해 보이는 표현을 평가기가 추측하도록 만드는 기능이
아닙니다. 사람이 사전에 동일한 정규화 결과라고 승인한 문자열만 기록합니다.
선택형 enum 필드는 한 케이스에 canonical value 하나만 허용해, 한 문장으로 여러
선택지 coverage를 부풀리지 못하게 합니다.

`JSON Schema`는 편집기가 작성 도중 필수 키, 값의 타입, 허용된 선택지를 알려 주는
설계도입니다. 실제 최종 검증은 Python 계약이 담당하지만, 작성 전용 Schema도 같은
코드에서 생성하고 자동 검사해 두 규칙이 따로 바뀌지 않게 합니다.
`authoring_schema_version: 2`는 사람이 편집하는 그룹 파일에서 split을 분리한
형식이고, `split_assignment_schema_version: 1`은 별도 split 원장 형식의 첫
버전입니다.
`dataset_version: 2`와 공식 프로필 V2는 컴파일된 평가 corpus와 채점 계약의
버전입니다. 서로 다른 대상을 관리하므로 숫자가 같을 필요는 없습니다.

같은 입력이 development와 test에 함께 들어가는 일을 **data leakage**라고 합니다.
코드는 유니코드 표기만 다른 경우까지 포함해 완전히 동일한 모델 입력이 corpus에
두 번 들어오는 것을 그룹 ID와 split에 관계없이 차단합니다. 같은 입력을 반복해서
실행하며 안정성을 측정하려면 데이터를 복제하지 않고 runner의 반복 실행 횟수로
관리해야 점수의 가중치가 임의로 바뀌지 않습니다.
뜻이 비슷하지만 문장이 다른 near-duplicate는 고정 유사도 임계값으로 추측하지
않고 작성자가 같은 의미 원본 그룹에 배정합니다.

마지막으로 coverage는 시험 범위가 빠지지 않았는지 확인할 뿐 표본이 통계적으로
충분하다는 뜻은 아닙니다. 먼저 계약에서 도출한 상태-행동·행동-필드·선택값을
모두 포함하고, 파일럿에서 실제로 나타난 오류율과 모델 간 차이를 근거로 독립된
대화 그룹을 늘립니다. 시나리오마다 임의로 같은 개수를 정하지 않습니다.

여기서 **작성 의무(obligation)**는 시험지에 반드시 한 번 이상 등장해야 하는
계약 항목입니다. 현재 V2에는 상태-행동, intent, 필드 있음·없음, 선택값, 변경
대상, 행동-필드 조합, 난이도 태그를 합쳐 865개가 있습니다. 한 case가 여러 필드와
태그 의무를 동시에 만족할 수 있지만 상태-행동은 하나만 담당하므로 352개의
상태-행동 의무가 공식 test case 수의 구조적 하한이 됩니다.

**작성 원본**은 사람이 수정하는 의미 그룹별 JSON이고, **컴파일 산출물**은
평가기에서 읽도록 compiler가 정렬·검증해 만든 단일 JSON입니다. compiler는
모델을 실행하거나 점수를 계산하지 않습니다. 같은 작성 원본에서 항상 같은
순서와 JSON을 만드는 성질을 **결정론적**이라고 합니다. 의무 목록은 앞으로
무엇을 작성해야 하는지 보여 주고, coverage 결과는 실제 corpus가 그 의무를
충족했는지 보여 주므로 서로 다른 자료입니다.

## Q25. split 배정을 왜 별도 원장으로 먼저 고정하나요?

development는 문제를 만들고 디버깅하는 연습장, validation은 모델과 프롬프트를
고르는 모의시험, test는 마지막에 한 번 여는 봉인 시험지에 가깝습니다. 모델 결과를
본 뒤 어려운 test 문제를 development로 옮기면 점수가 좋아 보여도 공정한 비교가
아닙니다.

그래서 `AuthoringGroup`은 의미 원본과 시나리오만 소유하고 split은 별도의
`split-assignments.v1.json`만 소유합니다. compiler는 다음을 모두 검사합니다.

- 모든 작성 그룹이 원장에 정확히 한 번 있어야 한다.
- 실제 작성 그룹이 없는 원장 항목도 허용하지 않는다.
- 그룹 파일 안에서 split을 다시 적어 원장 값을 덮어쓸 수 없다.
- 원장 배정이 바뀌면 split 식별값과 compiled corpus가 함께 바뀐다.
- 공식 test 점수 계산 직전에 원장 식별값을 다시 대조한다.

여기서 **원장(ledger)**은 중요한 결정을 한곳에서 관리하는 기록부입니다.
**freeze(동결)**는 파일을 기술적으로 영원히 수정할 수 없게 만든다는 뜻이 아니라,
모델 결과를 보기 전에 배정을 커밋하고 변경 이력을 PR과 데이터 버전에 남긴다는
뜻입니다. SHA-256 식별값은 어느 배정을 사용했는지 확인하지만, 누가 수정했는지를
증명하는 전자서명은 아닙니다.
