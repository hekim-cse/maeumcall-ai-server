# MaeumCall AI Server 학습 가이드

이 문서는 구현 결과만 보여주는 대신, 주요 설계 결정을 질문과 답 형식으로 설명합니다.

## Q1. 왜 단순한 LLM 채팅 API가 아니라 LangGraph를 사용했나요?

예약은 `정보 수집 → 확인 → 가능 여부 조회 → 확정 → 종료`처럼 이전 상태에 따라 다음 행동이 달라집니다. 프롬프트 하나에 이 책임을 모두 넣으면 상태 전이가 모델 문장에 묻혀 테스트하기 어렵습니다. LangGraph는 노드가 수행하는 일과 edge가 허용하는 전이를 코드로 분리하므로, 잘못된 순서로 예약이 확정되는 문제를 테스트할 수 있습니다.

```python
builder.add_node("extract_info", extract_info_node)
builder.add_node("decide_state", decide_state_node)
builder.add_conditional_edges("decide_state", route_after_decide)
```

## Q2. 사용자 발화를 왜 JSON으로 변환하나요?

그래프가 자연어 문장을 직접 읽고 분기하면 분기 조건이 문자열 검색에 의존합니다. 대신 모델이 `date`, `time`, `user_action` 같은 계약을 반환하고 서버가 이를 검증하면, 그래프는 타입이 확인된 데이터만 다룹니다.

```python
result = complete_validated_json(
    messages,
    completion=complete_hf_json,
    validator=validate_reservation_turn,
)
```

## Q3. 모델 출력이 잘못되면 왜 기본값으로 계속 진행하지 않나요?

`user_action=unknown` 같은 값을 자동으로 넣고 성공 응답을 반환하면 모델 장애가 정상 대화처럼 보입니다. 날짜나 확정 의도를 잘못 채우는 것은 더 위험합니다. 이 서버는 검증 오류를 포함해 한 번 재요청하고, 두 번째 출력도 잘못되면 타입이 있는 오류를 API 경계까지 전달합니다.

## Q4. 왜 JSON 코드블록을 서버가 알아서 벗기지 않나요?

서버가 모델의 계약 위반을 계속 보정하면 허용 범위가 점점 넓어지고 품질 저하가 지표에 잡히지 않습니다. 출력 계약이 “JSON 객체 하나”라면 markdown이 섞인 결과는 실패입니다. 재시도 프롬프트에 원인을 알려 모델이 계약을 지키게 하고, 반복 실패는 관측 가능한 오류로 남깁니다.

## Q5. 예약 응답은 왜 LLM이 아니라 응답 정책으로 만드나요?

`예약 가능`, `예약 완료`는 창의적으로 생성할 문장이 아니라 서버 상태가 보장해야 하는 사실입니다. 모델은 발화 이해에 사용하고, 확정된 상태를 사용자 문장으로 표현하는 일은 도메인 정책이 담당합니다.

```python
if conversation_state == "reservation_confirmed":
    return f"{date} {time} {department} 진료로 예약 완료됐습니다."
```

이 분리는 모델이 존재하지 않는 시간이나 예약 결과를 만들어내는 것을 구조적으로 막습니다.

## Q6. 자유 대화 시나리오는 어떻게 다르게 처리하나요?

가족·친구·연인처럼 정답 문구가 없는 상황은 모델 생성이 필요합니다. 이때도 자유 문자열만 받지 않고 `action`, `response`, `etiquette_tip`을 하나의 JSON 객체로 검증합니다. 종료 판단과 실제 응답이 같은 모델 결과에 포함되므로 상태와 문장이 일치합니다.

## Q7. 모델을 끈 단위 테스트가 의미 있나요?

의미 있습니다. 단위 테스트의 목적은 모델 품질이 아니라 우리 코드의 상태 전이, 라우팅, 오류 처리를 재현 가능하게 검증하는 것입니다. 모델 경계에는 고정 JSON을 주입하고, 실제 모델 호환성은 별도의 integration test로 검증합니다.

```bash
pytest -q
HF_LOCAL_MODEL_ENABLED=1 pytest -m integration -q
```

## Q8. 왜 미등록 시나리오를 일반 채팅으로 처리하지 않나요?

우회 처리를 허용하면 모바일 제목 변경이나 레지스트리 누락이 배포 후에도 발견되지 않습니다. 미등록 조합은 `422 UNSUPPORTED_SCENARIO`로 실패시켜 클라이언트와 서버 계약 불일치를 바로 드러냅니다.

## Q9. 이 구조를 다음 단계에서 어떻게 확장해야 하나요?

우선순위는 다음과 같습니다.

1. 노드별 latency, 모델 재시도, 계약 검증 실패 지표를 수집합니다.
2. 시나리오별 골든 데이터셋으로 `user_action`과 필드 추출 정확도를 평가합니다.
3. 배포 환경에서 사용하는 실제 모델 버전과 프롬프트 버전을 응답 로그에 연결합니다.
4. 다중 기기 재개나 노드 단위 복구가 제품 요구사항이 되면 영속 checkpointer와 인증된 `thread_id`를 도입하고 API 계약 버전을 올립니다.

새 기능을 추가할 때는 “모델이 판단할 일”, “그래프가 보장할 일”, “도메인 정책이 표현할 일”을 먼저 나누는 것이 핵심입니다.

## Q10. 음성의 pitch, jitter, shimmer로 불안이나 자신감을 판단할 수 있나요?

이 서버에서는 그렇게 판단하지 않습니다. 녹음 환경, 화자 특성, 건강 상태처럼 통제되지 않은 변수가 많으므로 고정 임계값으로 심리 상태를 단정하면 근거 없는 피드백이 됩니다. 서버는 측정값과 사용자 자신의 기준선 대비 변화만 반환합니다. 심리 상태 분류가 필요하다면 별도의 라벨 데이터, 평가 지표, 동의 절차를 갖춘 모델 검증 과제로 분리해야 합니다.

## Q11. 모델과 프롬프트 버전은 왜 함께 고정해야 하나요?

모델 저장소의 기본 브랜치는 같은 모델명 아래에서도 바뀔 수 있습니다. 이 프로젝트는 Hugging Face 모델명과 커밋 리비전을 환경 설정에 함께 기록하고, 원격 사용자 코드 실행 없이 표준 Transformers 구현을 사용합니다. 그래야 개발 환경과 CI에서 어떤 가중치와 토크나이저를 대상으로 검증했는지 설명할 수 있습니다.

## Q12. 왜 현재 LangGraph checkpointer를 바로 붙이지 않았나요?

현재 API는 모바일이 직전 `scenarioState`를 저장해 다음 요청에 전달합니다. 여기에 서버 checkpointer까지 추가하면 같은 상태의 원본이 두 개가 되고, 충돌 시 어느 쪽을 선택할지 별도 규칙이 필요합니다. 프로세스 재시작 시 사라지는 메모리 checkpointer는 운영 영속성도 제공하지 못합니다.

그래서 2.1에서는 클라이언트 소유 상태를 `scenario_key`, `state_version`, 필드 allowlist로 엄격하게 검증합니다. 서버 소유 상태가 필요해지는 시점에는 영속 저장소, 인증된 세션 식별자, 보존·삭제 정책을 함께 설계하고 계약 버전을 올립니다.

## Q13. 실제 사용자 ID를 파일 키로 저장하면 왜 안 되나요?

기준선 값 자체뿐 아니라 저장 키도 개인을 연결하는 식별 정보가 될 수 있습니다. 서버는 원본 ID를 저장하지 않고, 운영 비밀값을 키로 사용하는 HMAC-SHA256 결과를 저장 키로 사용합니다. 단순 SHA-256은 ID 후보를 대입해 같은 해시를 만들 수 있으므로 충분하지 않습니다. 비밀값이 없으면 임의의 기본값으로 실행하지 않고 `503 VOICE_BASELINE_SECURITY_NOT_CONFIGURED`로 실패합니다.

## Q14. 공백으로 단어를 나누면 왜 한국어 빈도 분석이 부정확한가요?

한국어의 조사와 어미는 앞말에 붙습니다. 예를 들어 `학교에서`와 `학교를`을 공백으로 나누면 서로 다른 단어가 되지만, 형태소 분석 결과에서는 둘 다 `학교/NNG`와 조사로 분리됩니다. 서버는 Kiwi가 반환한 형태소 원형과 품사를 사용해 이 문제를 해결합니다.

내용어는 명사·동사·형용사·부사처럼 코드에 공개한 품사 집합으로 정의하고, 군더더기 표현은 감탄사 품사 `IC`로만 집계합니다. 과거처럼 `그냥`, `좀`, `약간`을 고정 목록에 넣어 문맥과 무관하게 군더더기로 판정하지 않습니다. 한 글자 명사도 의미가 있을 수 있으므로 글자 수 필터도 사용하지 않습니다.

Kiwi가 설치되지 않았거나 분석 중 오류가 나면 공백 분리 결과를 정상 응답처럼 반환하지 않습니다. `/health/ready`의 `korean_text_analyzer`가 준비되지 않은 상태를 알리고 API는 `KOREAN_TEXT_ANALYZER_UNAVAILABLE` 또는 `KOREAN_TEXT_ANALYSIS_FAILED`를 반환합니다. 따라서 운영자는 분석 품질이 바뀐 사실을 즉시 알 수 있습니다.

## Q15. 통화 시작 전에 시나리오를 왜 다시 검증하나요?

모바일 앱과 서버는 같은 시점에 배포된다는 보장이 없습니다. 오래된 앱이 삭제된 시나리오를 보내거나 요청이 직접 조작될 수도 있습니다. `/call/setup`은 중앙 LangGraph 레지스트리에서 `category + title`을 검증하고, 서버가 확정한 `scenario_key`와 버전이 붙은 통화 계획만 반환합니다.

통화 방향 정책도 별도 문자열 조건문으로 추측하지 않습니다. 32개 등록 시나리오 각각이 정확히 하나의 통화 정책을 가지는지 초기화와 테스트에서 비교합니다. 모바일은 같은 시나리오의 준비 요청이 동시에 들어오면 진행 중인 Future를 공유하므로 네트워크 요청을 중복 전송하지 않습니다.

## Q16. 테스트가 통과하는데 정적 분석도 필요한가요?

테스트는 실행된 경로의 결과를 검증하지만, 호출되지 않은 코드의 미정의 이름이나 미사용 import, 파일별 형식 불일치를 모두 찾지는 못합니다. Ruff는 Python 3.11을 기준으로 이러한 문제를 검사하고, 로컬 `make lint`와 GitHub Actions가 같은 명령을 실행합니다.

외부 GitHub Action은 `@v6`처럼 나중에 다른 코드로 이동할 수 있는 태그 대신 검증한 릴리스의 40자리 커밋 SHA로 고정합니다. 버전 주석은 사람이 업데이트 대상을 읽기 위한 정보이고, 실제 실행 코드는 SHA가 결정합니다.

## Q17. 외부 시스템이 없는데 환불 승인이나 A/S 접수 완료를 만들면 안 되나요?

전화 연습 서비스 안의 모의 결과로는 만들 수 있습니다. 문제는 그 결과를 실제 주문·결제·기관 시스템의 처리라고 표현하는 것입니다. 서버는 모든 `/chat` 응답에 `simulation.externalEffect=false`를 넣고, 완료 문장에도 실제 시스템에 반영되지 않았다고 표시합니다.

업무 그래프는 정보가 모였다는 이유만으로 바로 완료하지 않습니다. 사용자가 내용을 확인하면 `ready`, 다시 모의 처리를 진행해 달라고 명시하면 `completed`로 전이합니다. 이 두 단계를 분리하면 “정보 확인”과 “행동 승인”을 각각 테스트할 수 있습니다.
