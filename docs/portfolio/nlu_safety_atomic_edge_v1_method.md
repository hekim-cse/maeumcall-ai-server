# A/S 위험 사건→주체 분리 개발 진단 설계

> 2026-11-18 설계. 이 단계에서는 모델을 실행하지 않았다. ES01–ES20은 AI 작성·사용자 검수 후 이미 여러 모델 실험에 노출된 개발 자료다. 아래 지표는 공식 정확도나 일반화 성능으로 사용할 수 없다.

## 근거와 변경 범위

기존 [연결 그래프 실험](nlu_safety_evidence_graph_v1_development_result.md)은 A와 E를 제공하고 모델에 B, E→B 연결, B→A 연결의 다섯 필드를 한꺼번에 요청했다. 출력 계약은 4/19건만 통과했고 B 원문 구절의 정답 정확 일치는 0/18건이었다. [명시 근거 규칙 기준선](nlu_safety_explicit_baseline_v1_development_result.md)은 검수된 B를 입력받아 관계 4/19건을 맞혔지만 E→B를 시험하지 않았다. 서로 입력 조건이 달라 두 점수의 차이를 개선율로 계산하지 않는다.

이번 후보의 **첫 단계**는 검수된 원문, 접수 제품 A, 사건 E와 발생 상태만 입력받아 B 원문 구절과 E→B 연결 종류·근거만 출력한다. 정답 B, 관계, 정답 근거 유형, 기대 경로는 예측 입력에서 제외한다. 두 번째 B→A 단계는 첫 단계의 출력 계약·의미 진단을 확인한 뒤 별도로 설계한다. 처음부터 두 단계를 다시 합쳐 실행하지 않는다.

## 계약과 평가 단위

- 출력은 B 구절, `subject|location|implicit|unresolved`, E→B 근거 구절로 제한한다. 인용 구절은 원문 문장 번호와 내용이 정확히 일치하고 해당 문장 안에서 유일해야 한다.
- `subject`와 `location`은 E·B를 모두 포함하는 국소 근거를 요구한다. `implicit`은 앞문장 선행사를 가리킬 수 있어 E와 같은 문장에 있다는 조건을 강제하지 않는다. 인용의 존재는 의미상 연결의 증명이 아니다.
- `unresolved`는 B·근거를 공란으로 둔다. 사건이 발생하지 않은 경우에는 모델을 호출하지 않고 관계를 공란으로 유지한다. ES17의 관찰된 사건·출처 불명과 ES18의 발생 불확실·현재 제품 관계는 다른 층위이므로 분리한다.
- 적격 호출은 ES 20사례·22사건 중 관찰 또는 불확실 사건 19건이다. 미발생 3건은 호출 대상에서 제외한다. 비공란 B 엄격 일치 분모는 18건, 공란 B 분모는 1건이다. E→B 종류와 인용 정확 일치, 계약 통과, 오류 코드는 각기 분리해서 집계한다. ES06처럼 두 사건이 한 발화에 있어도 사건 단위 분모를 사례 단위 경로 분모로 바꾸지 않는다.
- [기존 검수된 19건 연결 라벨](nlu_safety_evidence_graph_v1_field_review.md)은 **채점에만** 쓴다. 원문과 인용 위치를 정적으로 검증하고, 모델 요청 생성 함수에 정답 B·연결 종류·근거가 들어갈 수 없도록 입력 경계를 확인한다. 정답의 원문 위치가 유효하다는 사실은 연결 의미의 타당성을 추가 입증하지 않는다.

## 실행 전 결정과 판정

코드·검수 자료·요청 설정·모델 파일 해시, 사건 순서, 오류 시 보수적 경로, 독립 검증 방법을 모델 실행 전에 별도 프로토콜로 고정한다. 원시 응답은 저장소 밖 소유자 전용 위치에 보관하고 공개 저널에는 원문과 프롬프트를 넣지 않는다. ES에서는 계약 오류 0/19, B 18/18 및 출처 불명 공란 1/1, E→B 종류 19/19를 다음 B→A 단계로 넘어가기 위한 개발 관문으로 둔다. 이 문턱은 안전 배포 기준이 아니며, 실패하면 그 원인을 근거 추출과 연결 의미별로 나누어 기록한다. 해당 문턱을 바꾸려면 실행 전에 사유와 함께 프로토콜을 새로 고정한다.

이 개발 자료에서 후보를 선택한 뒤에는 새 발화와 전체 정답을 모델 실행 전에 사용자에게 검수받고 별도 미노출 평가를 수행한다. AI 작성 발화라면 출처를 명시한다. TX·GB 봉인 자료는 이번 후보 설계·선택과 평가에 사용하지 않는다. 기존 서비스 안전 분기는 건드리지 않는다.
