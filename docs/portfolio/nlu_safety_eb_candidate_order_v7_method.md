# A/S 위험 주체 원문 후보 목록·순서 대조 개발 진단 설계

> 2026-11-21 모델 실행 전 설계. 검수된 PC01·NC01 두 문장을 재사용하는 개발 진단이다. 공식 정확도·개선율, 새로운 일반화 성능 또는 서비스 안전 성능의 근거가 아니다.

## 질문과 선행 관문

[v5 양성·음성 대조](nlu_safety_atomic_edge_controls_v5_development_result.md)에서는 PC01도 `unresolved`·공란을 내어 당시 사전 지정한 후보 선택 진입 관문을 **통과하지 못했다**. [v6 형식 오라클](nlu_safety_atomic_edge_format_oracle_v6_development_result.md)은 정답 JSON을 준 경우 객체 출력이 가능함을 보였지만, 정답을 평문으로 준 경우에는 주체 구절을 과다 인용했다. 따라서 기존 관문을 통과한 것으로 소급하지 않는다. [기존 후보 ID 감사](nlu_safety_candidate_probe_offline_audit_result.md)에서는 RE/V E/B/C 정답 18구간 중 13개가 후보에 있어도 모델의 정확 선택은 0/13이었다. 이번에는 **정답을 주지 않는 별도 소규모 개발 진단**으로, 원문에서 자동 생성한 후보 목록이 단순 양성 사례의 비공란 선택을 돕는지와 목록 순서가 답에 영향을 주는지 본다.

## 고정 대조군과 조건

- [기존 검수 PC01·NC01](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-controls-v5-cases.json)을 그대로 사용한다. PC01은 B=`선풍기 모터`, 종류=`location`; NC01은 B 공란·`unresolved`다. 두 사례의 원문·A·E·발생 상태만 요청 생성에 쓰고, 정답 필드는 채점에만 쓴다. 두 사례를 ES/RE/V 분모에 섞지 않는다. TX·GB 봉인 자료는 사용하지 않는다.
- **A 기준선:** v4/v5의 두 필드 주체 단독 메시지와 JSON 스키마를 그대로 사용한다. 이번 실행의 A 응답을 기존 v5 저장 응답과 구분해 보고한다.
- **B 원순 목록:** 동일한 기본 메시지 끝에 `source_lattice.py`가 원문만 보고 만든 전체 원문 구절 후보를 ID·문장 번호·인용문으로 덧붙인다. 후보를 정답 표시로 취급하지 않고, 출처를 알 수 없으면 기존처럼 공란·`unresolved`를 허용한다. 반환 필드와 JSON 스키마는 A와 같다. 따라서 이 조건은 앞선 RE/V의 **ID 반환 계약**을 직접 재시험하지 않는다.
- **C 역순 목록:** B와 **같은 후보·ID·문구·JSON 스키마**를 유지하고 목록 행의 표시 순서만 뒤집는다. ID 자체는 바꾸지 않는다. B/C는 한 사례에서 목록 위치 민감도를 보는 대조이며, 두 번의 모델 응답만으로 인과나 편향의 크기를 추정하지 않는다.
- 후보 생성은 `max_window_tokens=5`, `max_candidates=192`로 고정한다. PC01 정답 후보의 포함 여부와 후보 수는 **원문 생성 후** 점검하고, NC01의 목록은 주체 정답을 강제하지 않는다. 후보가 없거나 정답이 목록에 없으면 그 상태를 그대로 보고한다. 모델 입력에는 정답·정답 ID·채점 결과를 넣지 않는다.
- PC01은 A→B→C, NC01은 C→B→A 순서로 총 6회 각 한 번 호출한다. 오류가 나도 고정 순서를 진행하고 재시도·부분 실행 재개는 하지 않는다. 두 사례의 순서를 반대로 해 목록 조건의 실행 위치를 완전히 같게 만들지는 못한다.

## 실행 전 고정과 독립 검증

코드·이 문서·기존 검수 사례를 먼저 커밋한다. 깨끗한 작업 트리에서 모델 SHA-256, 컨테이너 이미지와 고정 소스·입력 바이트를 확인한다. 여섯 요청 본문의 SHA-256, 후보 목록의 원문 해시·개수·순서, 호출 순서, 생성 정책을 별도 프로토콜에 기록해 **모델 호출 전에 커밋**한다. 기본 요청과 목록 요청 모두 로컬 127.0.0.1 전용 Q5, 같은 이미지·CPU·메모리·컨텍스트·생성 설정을 사용한다. 모델 호출 전 Q5의 실제 토크나이저와 대화 템플릿을 적용한 입력 토큰 수에 최대 생성 320토큰을 더해 4,096토큰 문맥 안에 드는지 점검한다. 실제 토큰 수를 확인할 수 없다면 제한을 통과했다고 주장하지 않고 호출을 중단한다.

공개 저널에는 원문·프롬프트·응답을 넣지 않고 요청·응답 해시와 실행 메타데이터만 둔다. 원시 응답은 저장소 밖 권한 제한 폴더에 둔다. 독립 검증기는 여섯 요청과 후보 목록을 다시 만들고 프로토콜·저널·원시 응답의 해시, 순서, 출력 계약과 정답 일치를 계산한다. 기존 v4/v5/v6의 방법·프로토콜·저널·원시 응답은 바꾸지 않는다.

## 사전 지정 지표와 중단 기준

조건·사례별 전송·종료 오류, 두 필드 출력 계약, 유효한 비공란·공란, PC01의 B 구절 정확 일치와 종류 일치, NC01의 유효한 `unresolved`·공란 및 근거 없는 비공란, 후보 수·정답 후보 위치를 **각각** 기록한다. 인용이 원문에 존재하는 것과 정답인 것은 구분한다. 정확하지 않은 부분 구절이나 과다 인용은 사후 허용값으로 승격하지 않는다. 지연은 기술 기록이며 토큰 수를 수집하지 않으면 추정하지 않는다.

B와 C의 양성 PC01이 모두 계약 유효·정확 B·정확 종류이고 음성 NC01에서 둘 다 유효 보류해야만 **후보 목록 인터페이스의 다음 개발 실험 진입 신호**로 본다. A와 비교한 단일 사례의 차이를 곧바로 목록 효과·순서 효과라고 확정하지 않는다. 어느 목록 조건에서든 PC01이 틀리거나 NC01을 근거 없이 확정하거나 계약 오류가 나면 큰 ES 묶음으로 확대하지 않고 그 실패를 분석한다. 이 작은 관문을 통과해도 E→B 전체 성능, B→A 또는 최종 안전 경로는 확인되지 않으며 서비스에 연결하지 않는다. 새 후보 선택 후에는 미노출 사례·정답을 별도 검수·사전 고정해 평가해야 한다.
