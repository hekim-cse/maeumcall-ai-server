# A/S 출력 계약 실패의 개발 진단

이 문서는 [RF01–RF12 동결 평가](nlu_review_followup_run_log.md)를 수정하거나 다시 채점하지 않는다. RF02·RF06은 이미 모델에 노출된 사례이므로 아래 재실행은 개발 진단이다.

## 확인한 원인

동결 평가에서 최종 코드 `ae91656`은 RF02·RF06의 두 시도 모두 `ValueError`로 계약 검증에 실패했다. 원문 응답을 보존하지 않았기 때문에 당시 결과 파일만으로 세부 원인을 알 수 없었다. 이후 같은 두 발화를 로컬 Kanana Q5에 다시 실행해 메모리 안에서 검증 오류를 확인했다. 두 사례 모두 모델이 `provide_details`를 선택하면서 이번 발화의 필드를 전부 공란으로 제출했고, `provide_details requires at least one current-turn field` 규칙을 위반했다. 진단 중 프롬프트와 응답 원문은 파일에 저장하지 않았다.

## 수정 근거와 확인 범위

현재 발화에서 새 필드가 하나도 없으면 `provide_details`는 정보 제공 계약을 위반한다. 한 후보 구현은 검증 직전에 이 조합을 `unknown`으로 정규화하고 필드를 공란으로 유지했다. 실제 필드가 하나라도 있는 `provide_details`와 필드를 담은 `unknown`의 검증은 유지했다.

그 후보를 적용한 뒤 동일한 로컬 Q5와 요청 설정으로 RF02·RF06을 재실행하자 두 사례 모두 첫 시도에 출력 계약을 통과했고 `unknown`으로 정규화됐다. 이는 노출된 두 사례의 개발 진단이며, 새 사례의 정확도 또는 전체 16개 업무의 개선율은 아니다. 이후 [새 SC 사례 짝비교](nlu_safety_contract_graph_pair_run_log.md)에서도 후보의 범위 밖 4건 계약 통과는 2/4에서 4/4로 늘었다.

**리뷰 후 운영 코드에서는 이 정규화를 철회했다.** 필드가 전부 공란인 이유가 업무 범위 밖인지, 업무 안의 제품 정보를 모델이 놓친 것인지 이 출력만으로는 구별할 수 없다. 후자를 `unknown`으로 조용히 통과시키면 추출 실패를 숨긴다. 현재 코드는 계약 위반을 재시도 경로에 남기고, 두 번째 시도도 실패하면 오류를 반환한다. 위 수치는 철회한 후보 코드 `9eacb92`의 실험 결과로만 보존한다.

## 다음 평가의 조건

범위 밖 요청을 안전하게 처리할 다음 방법은 새 발화를 모델에 보내기 전에 문장·행동·모든 필드의 정답을 검수하고, 데이터와 실행 조건을 동결해 다시 평가해야 한다. 기존 RF·SC 사례는 이미 모델에 노출돼 개발·회귀 용도로만 쓴다.
