# A/S 위험 사건 오라클 입력 조건부 출처 진단 설계

> 2026-11-15 모델 실행 전 기록한 개발 진단 계획이다. ES01–ES20은 이미 [v4 탐색 평가](nlu_safety_event_source_v4_exploration_result.md)에 사용한 AI 작성·사용자 검수 자료다. 재사용 결과는 일반화 성능이나 공식 정확도가 아니다. TX·GB 봉인 자료는 후보 선택에 사용하지 않는다.

## 확인하려는 문제

v4는 일반 고장·수리 발화를 위험 사건으로 추가하거나 두 사건을 한 구절로 합쳤고, 위험 출처도 잘못 연결했다. 두 단계가 함께 틀린 출력에서 한 단계만의 책임을 확정할 수 없다. 이번 조건은 사용자가 검수한 위험 사건 E와 발생 상태만 2단계에 제공해 **그 조건에서 제품 출처 관계가 어떻게 달라지는지** 진단한다. 실제 서비스는 이 정답을 받지 못하므로 배포 후보가 아니다.

## 입력과 실행

- 검수된 20문장·22사건 중 `observed` 또는 `uncertain`인 사건 **19개**마다 로컬 Kanana Q5의 기존 v4 2단계 계약을 한 번 호출한다. `nonoccurring` 3개는 모델을 호출하지 않는다. ES19·20은 해당 사례 전체가 무호출이므로 두 사례의 일반 경로는 모델 판단 성과로 세지 않는다.
- 각 요청에는 원문 전체, 검수된 접수 대상 A, **해당 사건의 검수된 원문 구절과 발생 상태**만 넣는다. 검수된 발생 물건 구절, `current`·`other`·`unknown` 관계, 기대 경로는 프롬프트에 넣지 않는다. 모델이 반환한 발생 물건 구절은 원문에 고정되는지 검증하되 의미 정답은 별도로 비교한다.
- 사건별 모델 관계와 검수된 발생 상태로 경로를 결정한다. 관찰된 현재 제품 위험이 하나라도 있으면 안전 우선, 출처 불명·현재 제품 위험 가능성이 남은 불확실성·오류는 안전 확인, 그 외는 일반 접수다. 오류 시 재시도하지 않는다.
- 기존 v4와 동일한 모델 파일·llama.cpp 이미지·CPU 2개·메모리 4GiB·컨텍스트 4096·온도 0·요청 정책을 사용한다. 코드·입력·모델·검증기를 커밋으로 고정하고 별도 프로토콜을 커밋한 뒤 한 번 실행한다. 원시 응답은 저장소 밖 소유자 전용 폴더에 보존하고 공개 저널에는 해시·길이·유한 오류·원문 구간 위치와 집계만 남긴다. 독립 검증기가 원시 응답부터 다시 계산한다.

## 사전 진단 기준과 보고 범위

사건별 출처 관계의 분모는 관찰된 현재 제품 **8개**, 관찰된 다른 제품 **9개**, 관찰됐지만 출처 불명 **1개**, 발생 불확실한 현재 제품 **1개**다. 각 범주를 전부 맞히고 계약·전송 오류가 **0/19**일 때만 조건부 관계 게이트를 통과했다고 기록한다. 모델 호출이 필요한 **18/18개 사례의 경로**와 출처 대비쌍 **2/2쌍**도 별도 게이트로 둔다. 대비쌍은 두 사례의 모든 호출 대상 사건에서 출처 관계가 맞고 두 최종 경로도 맞을 때 한 쌍을 통과한 것으로 센다. 무호출 ES19·20의 결정적 경로 2/2는 이 게이트의 모델 성능 분모에서 제외한다. 통과 여부와 별개로 19개 전체 관계, 발생 물건 인용의 엄격 원문 구절 일치, 현재 위험 즉시 대응 8건, 다른 제품만 위험한 사례의 잘못된 직접 경고, 불확실 사례 2건의 확인 경로를 각각 보고한다. 총 요청 수와 요청 지연 및 사례 전체 지연의 중앙값·95백분위를 구분해 남긴다.

같은 ES 사례의 v4 최종 경로 7/20과 이번 경로를 짝지어 오류 이동을 관찰할 수는 있다. 그러나 사건 구절과 발생 상태를 정답으로 주고 1단계 호출을 제거하며 호출 수도 바꾸므로 차이를 **1단계만의 인과 효과나 서비스 개선율**로 표현하지 않는다. 관계 게이트가 통과해도 실제 서비스 안전 분기에 연결하지 않는다. 출처 판단까지 실패하면 2단계 출처 귀속 자체의 오류를 분리해 다음 후보를 설계한다. 이 자료로 다음 후보를 조정하면 새 사례를 모델 실행 전에 다시 검수·고정해야 한다.
