# A/S E→B 후보 관계 판단 기준 명시 대조 설계

> 2026-11-23. 실모델 생성 전 설계다. 기존 v12의 네 쌍은 AI 작성·기노출 개발 사례이며, 사용자 검수 상태·근거 번호를 그대로 사용한다. 실서비스 코드와 안전 경로는 변경하지 않는다.

## 질문과 한 변수

[v12 개발 결과](nlu_safety_eb_pair_relation_v12_development_result.md)에서 후보 구절과 원문이 달랐지만 Q5는 네 쌍 모두 `supported`·2번 문장을 반환했다. 이는 입력 후보에 따른 구분 실패를 보여 주지만 스키마·프롬프트·모델 중 어느 하나가 단독 원인인지는 말하지 않는다. v12 스키마는 세 상태를 모두 허용했으므로 특정 상태를 **강제했다는 증거도 없다**.

이번 대조는 **시스템 메시지에 판단 기준 한 단락만 추가**한다. 후보 구절 전체가 물리적 출처인지 먼저 보고, 현상이 섞인 구절은 `unsupported`, 가능한 물체라도 사건 연결이 불명확하면 `insufficient`로 판단하도록 정의한다. 이는 네 사례의 답을 예시로 제공하는 방식이 아니라 기존 검수 기준을 일반 문장으로 명시하는 방식이다. 원문·사건 E·후보 ID/구절, 사용자 메시지, 응답 스키마, Q5 파일·서버 이미지, 생성 설정, 순서와 재시도 금지는 v12와 동일하게 둔다. 독립 검증기는 요청 JSON에서 **시스템 메시지 내용 이외에는 차이가 없는지** 확인한다.

## 실행과 해석 경계

v12 네 호출의 공개 프로토콜·저널 해시 및 비공개 원시 응답을 먼저 재검증한다. 새 요청은 PC01/P014 → PC01/P016 → NC01/P020 → NC01/P002 순서로 각 1회 실행한다. 생성 전 코드·데이터·요청 바이트·토큰 수·모델 파일·이미지를 별도 커밋으로 고정한다. 오류 시 첫 호출에서 중단하고 재시도하지 않는다. 원시 응답은 저장소 밖 제한 권한 폴더에 두고, 공개 저널에는 해시·오류·지연만 남긴다. AWS·KT cloud는 사용하지 않는다.

계약 통과, 상태 일치(4쌍), 근거 번호 일치(4쌍), `unsupported` 잘못 승인(2쌍), `insufficient` 잘못 승인(1쌍), 양성 거절(1쌍)을 따로 보고한다. 네 상태와 근거 번호가 모두 일치해야 개발 관문 통과다. 사후에 만든 프롬프트를 기노출 네 쌍에 시험하므로 **통과해도 공식 정확도·개선율이 아니다**. 개선되면 판단 기준 명시가 이 네 쌍에 도움을 준 것으로만 해석하고, 개선되지 않으면 이 한 문단의 추가가 충분하지 않았다고 해석한다. 스키마나 모델 자체가 원인인지까지 확정하지 않는다. 새로운 미노출 평가와 B→A·최종 안전 경로는 별도 단계다.
