# 행동 선택과 필드 추출 분리: 다음 개발 실험 계획

**상태: 실행 전 계획.** 2026-11-03 Q5·Q4 스키마 실험은 8건의 출력 계약 통과를
각각 3/8에서 8/8로 바꿨다. 같은 실행에서 행동 선택 또는 필드 초안 불일치가
남았으므로, 계약 통과와 의미 판단을 분리해서 관찰한다. 이 수치는 이미 노출된
AI 발화와 미확정 라벨에 대한 탐색 결과이며 정확도 개선율이 아니다.

## 오류를 나눠 볼 이유

`H13`–`H20`의 스키마 조건 결과에는 두 종류의 불일치가 있다.

| 구분 | 사례 | 현재 기록으로 확인할 수 있는 것 |
| --- | --- | --- |
| 행동 선택 | H14·H16 | Q4는 `cancel_workflow`, Q5는 `unknown`; 2026-11-04 사용자 판단 방향은 `unknown` |
| 행동 선택 | H19·H20 | 두 모델 모두 초안과 행동이 달랐다. H19는 `unknown`, H20은 `provide_details` 형태로 계약을 통과했다 |
| 필드 추출·정규화 | H13·H15·H17 | 행동은 `provide_details`였고, 각각 `delay_detail`, `requested_change`, `evidence_status`·`issue_detail`이 초안과 달랐다 |
| 대조군 | H18 | 두 모델 모두 `unknown` 형태로 계약을 통과했고 초안과 일치했다 |

결과 파일에는 모델이 만든 필드 **값**을 저장하지 않았다. 불일치 필드 이름만으로
모델 값과 초안 중 어느 쪽이 의미상 맞는지 결정하지 않는다. 사용자 확인은 행동과
핵심 필드의 방향에 한정되며 정규화 문자열은 계속 검토 대상이다.

## 비교 설계

1. 새 개발 사례를 준비하고, 모델을 실행하기 전에 문장·상태·행동·필드 라벨과
   검수 범위를 기록한다. AI 작성 발화는 출처를 그대로 표시한다.
   이번 개발 사례의 검수 범위는 [D01–D08 작업지](nlu_action_field_dev_review.md)에
   기록한다.
2. 동일한 모델 파일, 서버 이미지, 사례, 생성 설정에서 기존 한 번 생성 방식과
   **행동 먼저 선택 → 선택한 행동에 맞는 필드만 추출**하는 실험 방식을 실행한다.
   `change_detail`이 포함된 사례는 변경 대상 필드 선택도 첫 단계에서 검증한다.
3. 사례별로 행동 일치, 필드별 일치, 전체 라벨 일치, 출력 계약 통과, 생성 횟수,
   입력·출력 토큰 수와 요청 시간을 각각 기록한다. 생성된 발화·필드 값 전문은
   결과 파일에 남기지 않는다.
4. 행동이 틀렸지만 필드 제약으로 계약을 통과한 경우를 별도로 집계한다. 필드
   추출 단계의 이득과 행동 선택 단계의 오류를 합쳐 하나의 개선 수치로 쓰지 않는다.

새 사례에서는 Q4·Q5 각각에 대해 두 방식을 사례별 두 번 실행하고, 이웃 사례와
반복 사이에 실행 순서를 바꾼다. 모델 파일과 서버 이미지의 해시, 사례 파일과
실험 코드의 SHA-256, CPU·스레드·컨텍스트, 토큰·캐시·요청 시간, 재시도 횟수를
결과에 보관한다. 이 순서 교차만으로 캐시와 실행 환경의 영향을 완전히 제거했다고
주장하지 않는다.

기존 `H13`–`H20`은 이미 실패를 보고 선정한 진단 사례다. 구현 점검에는 쓸 수
있지만 최종 비교의 독립 사례로 재사용하지 않는다. 공식 전체 정확도 비교에는
별도의 사람 작성·검수·동결된 test 사례와 같은 조건의 두 방식 실행이 필요하다.

실험 방식은 서비스 호출 경로에 연결하기 전에 새 개발 사례에서 계약 위반,
행동 퇴보, 추가 생성 비용을 함께 검토한다.
