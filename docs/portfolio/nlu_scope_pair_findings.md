# 업무 범위 판단 수정 전후 비교

## 비교 범위

같은 Kanana Q5 GGUF 모델을 수정 전 서버 코드 `64fd849`와 업무별 지원
목적을 추가한 코드 `f52d991`로 실행했다. 16개 업무에서 업무 안 발화와
범위 밖 발화를 하나씩, 총 32건 사용했다. 발화는 AI가 작성했고
프로젝트 소유자 한 명이 문장·행동·필드·공란을 모델 실행 전에 채택했다.
독립적인 두 번째 검수자는 없었다.

데이터와 라벨 해시는 실행 전 커밋에 고정했다. 전후 조건은 같은 로컬
Q5 파일·요청 설정·Docker 이미지에서 사례마다 순서를 번갈아 실행했다.
메모리 부족으로 앞선 두 시도는 무효 처리했고, 세 번째 실행은 8개 사례
단위로 서버를 재시작해 64회 요청을 모두 완료했다. 이 운영상 변경은
[실행 기록](nlu_scope_pair_run_log.md)에 공개했다. 결과 파일의 점수는
별도 검증기로 다시 계산했으며 전송 오류는 없었다.

| 지표 | 수정 전 | 수정 후 | 관측 차이 |
| --- | ---: | ---: | ---: |
| 전체 행동 일치 | 18/32 (56.25%) | 23/32 (71.88%) | +15.63%p |
| 전체 완전 일치 | 4/32 (12.50%) | 9/32 (28.13%) | +15.63%p |
| 범위 밖 행동 일치 | 2/16 (12.50%) | 7/16 (43.75%) | +31.25%p |
| 범위 밖 완전 일치 | 2/16 | 7/16 | +5건 |
| 업무 안 행동 일치 | 16/16 | 16/16 | 변화 없음 |
| 업무 안 완전 일치 | 2/16 | 2/16 | 변화 없음 |
| 최종 출력 계약 통과 | 26/32 | 28/32 | +2건 |

완전 일치는 행동·의도·모든 필드의 값과 공란·변경 필드가 함께 맞은
사례 수다. 범위 밖 행동 정답은 `unknown`이다. 수정 후에는 범위 밖
사례 NS14·16·24·28·32에서 행동 오류가 바로잡혔다. 업무 안 NS15는
완전 일치로 바뀌었지만 NS11은 잘못된 `user_name` 값이 생겨 완전
일치에서 빠졌다. 따라서 개선만 있고 회귀가 없다고 설명할 수 없다.

32건의 짝비교에서 완전 일치는 6건 개선·1건 악화였고 정확한 양측
McNemar 검정값은 `p=0.125`였다. 행동 일치는 5건 개선·0건 악화,
`p=0.0625`였다. 작은 AI 작성·1인 검수 표본에서 관측된 차이이며,
전체 서비스 발화로 일반화하거나 통계적으로 확인된 개선이라고
주장하지 않는다. 앞선 무효 실행에서 같은 NS 사례가 모델에 일부
노출됐지만, 그 결과로 프롬프트·코드·정답을 조정하지 않았다. 변경된
것은 메모리와 계획된 서버 재시작뿐이다.

## 리뷰 후 코드와 수치의 경계

위 수치는 후보 프롬프트 커밋 `f52d991`의 결과다. 최종 실행 시 후보
작업자는 후속 커밋의 작업 트리에서 시작했지만, `f52d991`부터 평가
결과 커밋 `6c5a277`까지 `llm`, `services/flow`, NLU 채점·정규화 모듈과
기존 라이브 분석 실행기 Python 소스에는 변경이 없음을 Git diff로
확인했다. 평가 실행기가 생성한 프롬프트 해시도 `f52d991`과 일치했다.
v3 결과를 재현할 때는 프로토콜에 고정된 실행기 해시와 이를 포함한
커밋 `8c527b4`를 사용한다. 리뷰 후 실행기는 앞으로 후보 커밋의 별도
작업 트리를 요구하도록 강화했으며, 기존 v3 파일을 다시 쓰지 않는다.
리뷰 후 안전 이상 우선 처리와 면담 필드 안내를 수정하는 코드는
**이 수치의 평가 대상이 아니다.** 해당 수정이 실제 모델에서 나아졌다는
주장은 별도의 미노출 사례 평가 전에는 하지 않는다.

포트폴리오에는 다음처럼 범위를 붙여 쓸 수 있다.

> 모델로 수정 전후 코드를 비교했습니다. 업무별 지원 목적을 명시한 뒤
> 범위 밖 행동 일치는 2/16에서 7/16, 전체 완전 일치는 4/32에서

> 사례의 필드 오류가 새로 발생했습니다. 데이터·코드·실행 조건과
> 메모리 부족으로 무효 처리한 실행까지 기록해 결과의 범위를
> 구분했습니다.
