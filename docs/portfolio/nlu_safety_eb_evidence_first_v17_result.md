# A/S 원문 근거 우선 진단 결과

[사전 방법](nlu_safety_eb_evidence_first_v17_method.md)의 실행 코드는 `e2ca7fd`, [요청 프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-evidence-first-v17-protocol.json)은 첫 모델 호출 전 `88d5e87`에 고정했다. v16과 동일한 Kanana Q5 파일과 컨테이너 이미지를 사용했다. 네 후보에 정방향·역방향 질문을 차례대로 한 번씩 보냈으며, 각 후보의 두 조건은 사용자 메시지 안의 질문 순서만 다르다. 모델 서버가 보고한 입력 토큰은 후보별로 303·301·314·314개였고 두 조건에서 각각 같았다.

| 사전 지정 지표 | 정방향 | 역방향 |
| --- | ---: | ---: |
| 출력 계약 통과 | 4/4 | 4/4 |
| 관계 상태 정답 일치 | 1/4 | 1/4 |
| 근거 문장 번호 정답 일치 | 0/4 | 0/4 |
| 인용을 하나라도 반환한 응답 | 0/4 | 0/4 |

8개 원시 응답은 바이트 단위로 같았다. 세 인용이 모두 공란이어서 코드가 모두 `insufficient`로 분류했다. 정답이 일치한 NC01/P002도 명시된 불확실성 근거인 3번 문장을 놓쳤다. 출력 계약과 전송 오류는 0건이었고 재시도는 없었다. [저널](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-evidence-first-v17-journal.v1.jsonl)의 SHA-256은 `3838f35d9227fbcbbed43177483c13684e79e04fecefd3f23e0c876bed965bc1`이다. 저장소 밖에 보관한 원시 응답과 저널을 재생해 해시·판정·채점을 확인했다. 재생은 실행기와 같은 응답 계약을 사용한다.

기노출 후보 네 쌍에서 질문 순서를 바꿔도 결과는 같았다. 모든 사례에서 동일하게 판단을 보류했으므로 순서에 무관하게 유효한 근거를 찾았다는 해석은 할 수 없다. v16과 v17은 프롬프트와 출력 계약이 함께 달라져, 공란으로 수렴한 원인을 한 요소로 특정할 수 없다.

개발 관문을 통과하지 못해 이 후보의 새 미노출 평가와 서비스 연결은 보류했다. 다음 후보에서는 자유 문자열 인용의 부담을 줄이는 방법을 검토한다. 예를 들어 원문과 사건에서 만든 번호 근거 후보를 제시하고 선택·보류를 평가할 수 있다. 이때 후보 목록에 정답이 포함됐는지와 포함된 정답을 모델이 골랐는지를 따로 측정해야 한다. 이전 v10의 출처 ID 선택과는 평가 대상이 달라야 하며, 기존 실패를 피하는지 개발 대조에서 확인한다.
