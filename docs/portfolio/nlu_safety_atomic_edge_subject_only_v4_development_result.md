# A/S 위험 주체 단독 추출 개발 진단 결과

> 2026-11-20. 이미 노출된 AI 작성·사용자 검수 ES 사례 5건의 개발 진단이다. 공식 정확도·개선율, 새 사례 일반화 성능 또는 서비스 안전 경로 성능이 아니다.

## 실행과 독립 검증

- [실행 전 방법](nlu_safety_atomic_edge_subject_only_v4_method.md)에 따라 ES01·03·09·17·18의 첫 사건을 기존 세 필드 기준선 A와 주체·종류만 요구하는 B에서 각 한 번씩, 총 10회 호출했다. 두 조건 모두 JSON 스키마 제약을 사용했다. Q5 모델·이미지·자원·생성 설정은 같고 호출 순서를 미리 고정했다. 재시도는 없었다.
- 코드와 방법은 모델 호출 전 커밋 `d6cce1bb7e638897fe8e3d412979e0e5d587a384`에서 고정했다. [프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-subject-v4-development-protocol.json)은 별도 커밋 `e484bc8`에 선행 기록했고 SHA-256은 `1567f07e2e9d4123700005b05169178b5d95c1491a51bff1e12cda6aa2c05be4`다. 10개 요청 본문 SHA-256을 모델 실행 전에 고정했으며 A의 다섯 요청 해시는 [이전 v3 프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-format-v3-development-protocol.json)의 스키마 지정 기준선과 각각 같다.
- 모델 파일 SHA-256은 `644b04cde835d486df33c6d4d7552ba367fcb28802fe39b6b4bb9c60b9ab6f3d`, 컨테이너 이미지 digest는 `sha256:17155a3ce4cc906728ec99a2814bf0b4eaffaf3b4872bad8c3affed310cdbc35`다. 로컬 컨테이너에 CPU 2개·메모리 4 GiB와 127.0.0.1 전용 포트를 지정했다. 실행 뒤 컨테이너와 Docker Desktop을 종료했다. AWS·KT cloud는 사용하지 않았다.
- [공개 저널](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-subject-v4-development-journal.v1.jsonl)은 헤더 1행과 호출 결과 10행이며 SHA-256은 `1e6d6a7d5a11e4c7661840bf0485b3debbd98d27be5f4b250ea4359d2875e84c`다. 원문·프롬프트·응답을 포함하지 않는다. 원시 응답 10개는 저장소 밖 권한 제한 폴더에 보관했다. 검증기는 저널 행·요청·원시 응답의 해시와 순서를 검사하지만 저널 파일 **전체** SHA-256은 자동 대조하지 않으므로 재검증 때 위 값을 별도로 확인해야 한다.
- 독립 검증기는 원본 v3 프로토콜·저널 해시와 비공개 원시 응답을 확인하고, 이번 요청을 자체 재구성해 새 원시 응답과 검수 정답을 채점했다. A의 다섯 원시 응답은 이전 v3 A와 모두 바이트 단위로 일치했다. 검증기 SHA-256은 `31019323b691ee8c02c3f8ec3f5de7f8a3d4c6e101b2802a7afdfdfdbf09d410`이다. 실행 뒤 검증기 변경을 허용하는 구조이므로 재검증에는 이 해시를 함께 대조해야 한다.
- PR 리뷰 후 실행기는 로컬 Docker 컨텍스트·소켓을 요청 전에 확인하고, 저널 생성이 첫 호출 전에 실패하면 새 빈 비공개 폴더를 정리하도록 보강했다. 검증기는 로드 시점의 소스 SHA를 고정하고 재생 전후 파일 변경을 거부한다. **이 수정은 실모델 실행 뒤** 이뤄졌으며 고정 프로토콜·저널·비공개 원시 응답은 바꾸거나 모델을 재호출하지 않았다. 보강 실행기를 원본 고정 실행 코드라고 주장하지 않는다. 보강 검증기 SHA-256은 `473f9867e170a5bef0eda79a79abedb618cd821eab032a188a1e615b57219b31`이며, 보존한 응답을 다시 재생해 같은 집계를 얻었다. 관련 테스트 77개와 Ruff 검사가 통과했다.

## 고정 5건의 결과

| 지표 | 세 필드 기준선 A | 주체 단독 B |
| --- | ---: | ---: |
| 모델 호출 | 5/5 | 5/5 |
| 전송·종료 오류 | 0/5 | 0/5 |
| 출력 계약 통과 | 5/5 | 5/5 |
| 유효한 `unresolved`·주체 공란 | 5/5 | 5/5 |
| 비공란 B 원문 구절 정확 일치 | 0/4 | 0/4 |
| B 정답 대상 중 계약 유효 출력 | 4/4 | 4/4 |
| 연결 종류 일치 | 1/5 | 1/5 |
| ES17 정당한 보류 | 1/1 | 1/1 |
| 연결 근거 일치, 공란 포함 | 1/5 | 평가하지 않음 |
| 비공란 연결 근거 일치 | 0/4 | 평가하지 않음 |
| 요청 전송·응답 구간 지연 합계 | 26,068.872 ms/5회 | 16,684.960 ms/5회 |

B에서도 비공란 주체 정답 4건은 모두 보류했다. 따라서 사전 지정한 **탐색 신호**(B를 적어도 1건 유효하게 맞히고 ES17을 유효하게 보류)는 나타나지 않았고, 후보 관문(계약 5/5·B 4/4·종류 5/5·ES17 1/1)도 통과하지 못했다. ES17은 두 조건 모두 유효한 `unresolved`와 주체 공란으로 판단했다. B는 근거를 생성하지 않으므로 근거 점수를 매기지 않았다. 실행 전 방법 문서의 “B가 보류하거나”는 비공란 정답 사례의 전건 보류를 뜻한다. ES17의 **정당한** 보류는 탐색 신호의 필수 조건이며 진행 금지 사유가 아니다. 이 문구 해석을 실행 후 명확히 적되, 해시가 고정된 방법 문서 자체는 변경하지 않았다.

두 조건의 요청 지연 합계는 기술 기록이다. 사례가 5건뿐이고 조건별 요청 길이와 호출 순서가 달라, 이를 서비스 응답 속도 개선율이나 통계적 속도 차이로 해석하지 않는다. 전송 계층이 토큰 사용량을 보존하지 않아 토큰 수는 수집하지 않았다.

이번 비교는 프롬프트의 과제 요구와 스키마 필드 수가 함께 바뀐다. 결과는 **주체 단독 과제로 바꿔도 이 다섯 사례의 전건 보류가 해소되지 않았다**는 관찰이다. 근거 동시 요구가 보류의 원인인지 단정할 수 없다. 주체 단계가 사전 지정 신호를 내지 않았으므로, 모델이 생성한 B를 전제로 하는 근거 2단계는 이번에 진행하지 않는다. 원인 분석은 주체 후보를 찾는 입력·질문 방식 자체를 별도 변수로 고정해 이어가야 한다.

기존 19건 개발 관문은 여전히 미달이며 이 5건으로 대체하지 않는다. B→A 관계와 최종 안전 경로는 평가하지 않았고 서비스에 연결하지 않았다. TX·GB 봉인 자료는 사용하지 않았다. 공식 성능 주장은 새 미노출 검수 사례에서 별도로 평가해야 한다.
