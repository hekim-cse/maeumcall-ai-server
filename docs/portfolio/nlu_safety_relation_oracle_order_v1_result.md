# A/S 위험 출처 관계 판단의 정의 순서 민감도

> 2026-11-16. 이미 노출된 AI 작성·사용자 검수 ES 자료를 이용한 **Q5 주체 오라클 개발 진단**이다. 검수된 접수 대상 A, 위험 사건 E, 위험 주체 B와 발생 상태를 모델에 제공하고 관계만 물었다. 실제 서비스의 추출 성능이나 공식 전체 정확도를 측정한 결과가 아니다. TX·GB 봉인 자료는 사용하지 않았다.

## 실행과 검증 범위

[사전 설계](nlu_safety_relation_oracle_order_v1_method.md)에 따라 ES 20사례·22사건에서 미발생 사건 3개와 위험 주체가 공란인 ES17 사건 1개를 제외했다. 남은 **18사건/17사례**의 정답은 관찰된 현재 제품 8건, 발생 불확실한 현재 제품 1건, 관찰된 다른 출처 9건이다. 관계 기준 `current` 9건과 `other` 9건이므로 한 관계만 내는 상수 기준은 9/18이다. 각 사건을 동일한 Kanana Q5에 두 번 보냈으며, 두 조건의 차이는 관계 정의의 자연어 제시 순서뿐이다. JSON enum 순서·요청 설정·입력 필드는 같고 사건별 실행 선후를 번갈아 배정했다.

[동결 프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-relation-oracle-order-v1-development-protocol.v1.json)은 모델·서버 이미지·입력·코드 해시, 36회 호출 순서, 재시도 없음, 집계와 안전 경로 규칙을 기록한다. 프로토콜 SHA-256은 `eec2b728466c3f3e132dbe493d39ed82cc2c00f0d81204bda532dc1d0e298991`, 동결 코드 커밋은 `98114c8c1de19e279fa4cf6ce3ac33cbd55741cc`다. [공개 저널](../../evals/structured_nlu/data/ai_heldout/as-safety-relation-oracle-order-v1-development-journal.v1.jsonl)의 SHA-256은 `5da313cc52c3b1bd3742e80575b7e78d1871649c74f0058735d6fba645663f3f`다. [독립 검증기](../../experiments/as_safety_relation_oracle_order_v1/verify.py)가 저장소 밖 원시 응답 **36개**의 해시·권한, 호출 순서, JSON 계약, 사건별 관계와 사례별 경로, 요약을 재계산해 [검증 기록](../../evals/structured_nlu/data/ai_heldout/as-safety-relation-oracle-order-v1-development-verification.v1.json)과 일치했다. 원시 응답은 공개 자료에 포함하지 않는다.

## 실모델 결과

| 항목 | `current → other → unknown` | `unknown → other → current` |
| --- | ---: | ---: |
| 호출 및 단일 필드 JSON 계약 통과 | 18/18 | 18/18 |
| 관계 정답 | 11/18 | 13/18 |
| 관찰된 현재 제품 정답 | 8/8 | 4/8 |
| 발생 불확실한 현재 제품 정답 | 1/1 | 0/1 |
| 관찰된 다른 출처 정답 | 2/9 | 9/9 |
| 출력 분포 `current / other / unknown` | 16 / 2 / 0 | 4 / 14 / 0 |
| 17사례의 안전 경로 정답 | 11/17 | 12/17 |
| 대비쌍 전체 정답 | 0/2 | 1/2 |
| 현재 제품의 직접 위험 경로 누락 | 0사례 | 4사례 |
| 다른 출처를 직접 위험으로 오경고 | 6사례 | 0사례 |
| 요청 지연 p50 / p95 | 2.447초 / 4.310초 | 2.696초 / 3.797초 |

양쪽 모두 계약 오류와 응답 오류는 0건이었다. **같은 사건의 관계 출력이 두 조건에서 일치한 것은 6/18뿐**이다. 양쪽 모두 정답인 사건 6개, 첫 순서만 정답인 사건 5개(ES02·03·07·08·18), 역순만 정답인 사건 7개(ES06 첫 사건·09·10·11·13·14·16)였고 양쪽 모두 오답인 사건은 없었다. 역순의 전체 정답이 2건 더 많다는 이유로 역순을 우수한 프롬프트로 채택할 수 없다. 역순은 현재 제품의 관찰된 위험 4건을 놓쳤고, 불확실한 현재 제품 1건도 `other`로 분류했다.

첫 순서는 다른 출처 7/9사건을 `current`로 분류했지만 사례별 직접 위험 오경고는 6건이다. ES06에서는 다른 출처인 첫 사건을 오판해도 같은 사례의 현재 제품 위험 사건이 직접 위험 경로를 요구하므로 경로 집계가 이 오류를 가린다. ES01/09 대비쌍은 첫 순서에서 실패하고 역순에서 성공했다. ES02/11 대비쌍은 두 순서 모두 실패했다. 따라서 사례별 경로만으로 사건별 관계 판단을 평가하면 안 된다.

사전 등록한 개발 문턱은 **두 순서 각각** 범주별 8/8·1/1·9/9, 안전 경로 17/17, 대비쌍 2/2, 오류 0건과 사건별 두 순서 일치 18/18이었다. 실제 결과는 이 문턱을 통과하지 못했다. 관찰된 출력 쏠림과 12/18 사건의 순서 불일치는, 검수된 주체 B를 이미 제공해도 이 조건의 관계 판단을 안전 분기에 그대로 맡기기 어렵다는 개발 진단이다. 이 한 번의 실험으로 모델의 일반적 성질이나 순서 효과의 세부 원인을 단정하지 않는다.

## 해석 경계와 다음 결정

이번 조건은 **정답 B를 입력하는 오라클**이어서 B 추출 실패를 제거한 진단이다. 실제 서비스의 A·E·B 추출과 연결, 전체 NLU 정확도, 배포 안전성을 입증하지 않는다. ES17의 위험 주체 공란·정답 `unknown`을 제외했으므로 `unknown` 인식률이나 확인 경로의 해당 사례 성능은 측정되지 않았다. 기존 R·O 조건은 입력과 출력 계약이 달라 이번 11/18·13/18을 기존 점수와 빼서 개선율로 쓸 수 없다. ES 발화는 이미 모델 및 개발 과정에 노출된 AI 작성 사례라 새로운 일반화 정확도도 아니다.

다음에는 먼저 **관계 판단의 정의 순서와 선택 편향**을 개발 자료에서 통제한다. 정의 여섯 순열을 같은 사건에 짝지어 적용하고 호출 선후를 균형 있게 배정하면, 이번 두 순서의 차이가 특정 배열에 국한되는지 확인할 수 있다. 범주별 직접 위험 누락과 다른 출처 오경고를 최우선으로 보고, 후보를 고른 뒤에는 모델이 보지 않은 새 발화와 전체 정답을 사용자 검수·동결해 별도로 평가해야 한다. 두 출력이 다를 때 확인 경로로 보내는 보수적 규칙도 개발 가설로만 검토할 수 있다. 현재 자료에서 두 출력이 같은 6건은 모두 정답이었지만 표본이 작고 정답 `unknown`이 없어 그 규칙의 안전성을 보증할 수 없다.
