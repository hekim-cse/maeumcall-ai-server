# A/S 안전 근거 추출의 Q4·Q5 개발 짝비교

## 질문과 평가 경계

이전 [원문 구간 선택 진단](nlu_safety_evidence_development.md)은 출력 계약을 32/32건 통과했지만, Kanana Q5가 현재 제품의 위험 진술이 없는 12건 중 6건을 즉시 위험으로 분류했다. 양자화 수준을 달리한 같은 Kanana 모델에서 대상·태도 오류가 어떻게 바뀌는지 확인했다. 이미 여러 번 모델에 노출된 AI 작성·1인 검수 CF01–CF32를 다시 사용했으므로 **새 미노출 평가나 공식 정확도 개선율이 아닌 개발 진단**이다.

모델 파일·데이터셋·요청 정책·실행기와 검증기의 SHA-256, 컨테이너 이미지·메모리·CPU·포트와 호출 순서를 [프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-exposed-q4-q5-development-pair-protocol.v1.json)에 모델 호출 전에 커밋했다. 같은 llama.cpp 이미지에서 Q4와 Q5를 각각 4GiB·CPU 2개 한도의 로컬 서버로 실행했다. 한 사례마다 두 모델의 호출 순서를 교대했고, 결과에는 발화·모델 응답 전문을 저장하지 않았다. [결과](../../evals/structured_nlu/data/ai_heldout/as-safety-exposed-q4-q5-development-pair-result.v1.json)의 64회 호출 순서, 사례별 근거 번호, 경로, 실패, 구간별 집계는 별도 검증기로 재계산했다. AWS는 사용하지 않았다.

CodeRabbit 검토 후 검증기가 성공·실패 행 모두의 비유한 지연 값(`Infinity`·`NaN`)을 거부하도록 보강했다. 모델 호출 전 프로토콜에 기록된 검증기 해시는 당시 버전 `371bdbc...`의 이력이며, 보강된 현재 검증기 해시는 `e190f015e6aa47505e80c5a7cbd797714a2596cb6f36d482ee8907475a81a401`이다. 원본 프로토콜·64회 모델 호출·결과 파일은 수정하지 않았고, 보강된 검증기로 같은 결과를 다시 검증했다.

## 관찰 결과

| 검수 구간 | 목표 방향 | Q4 | Q5 |
| --- | --- | --- | --- |
| 실제 위험 12건 | 즉시 위험 대응 | 즉시 3, 일반 9 | 즉시 10, 일반 2 |
| 위험 여부 모호 8건 | 안전 확인 | 확인 4, 일반 4 | 즉시 2, 확인 4, 일반 2 |
| 현재 제품 위험 진술 없음 12건 | 일반 수집 | 즉시 4, 일반 7, 계약 실패 1 | 즉시 6, 확인 1, 일반 5 |

Q4의 출력 계약 통과는 31/32건이며 CF21에서 `ValueError`가 기록됐다. Q5는 32/32건 통과했고, 이전 Q5 원문 구간 진단의 대상·태도·근거 번호·경로와 32건 모두 동일했다. Q4는 실제 위험에 대한 즉시 대응을 7건 더 놓쳤고, Q5는 위험 진술이 없는 발화를 2건 더 즉시 대응으로 잘못 분류했다. 두 모델 모두 안전 경로에 적용할 근거가 없다.

유효 응답의 구간별 중앙 요청 시간은 실제 위험에서 Q4 997ms·Q5 1,307ms, 모호한 위험에서 1,049ms·1,398ms, 위험 진술 없음에서 1,088ms·1,371ms였다. 이 수치는 **로컬 단일 요청의 개발용 시간**이다. 컨테이너 두 개가 동시에 메모리에 적재된 조건이며 서비스 그래프 지연이나 사용자 응답 시간의 개선으로 해석하지 않는다. Q4의 실패 1건은 유효 응답 중앙값에서 제외했다.

## 결정

양자화를 Q4에서 Q5로 바꾸면 이 노출 사례에서는 실제 위험 감지가 늘지만 비위험의 즉시 차단도 늘어난다. 따라서 양자화 선택만으로 대상 제품·실제 발생·부정·가정 문맥을 해결할 수 있다는 근거가 없다. 다음 후보는 모델 응답을 바로 안전 상태로 옮기기 전에 **현재 제품의 실제 위험인지 확인 가능한 근거**를 별도 계약으로 검증해야 한다. 후보를 서비스에 연결하려면 코드와 요청 설정을 먼저 고정하고, 별도의 새 사례를 사용자 검수 후 실행해야 한다.
