# A/S 후보 관계 응답 경로 통제 검사

> 2026-11-24. 생성 전 설계. 기존 PC01/P014는 AI 작성·기노출 개발 사례다. 아래 두 출력은 **인위적으로 틀린 답을 유도하는 장치 점검**이며 정확도 평가가 아니다.

## 왜 검사하는가

[v12](nlu_safety_eb_pair_relation_v12_development_result.md)와 [v13](nlu_safety_eb_criteria_v13_development_result.md)은 후보와 판단 기준을 바꿔도 모두 같은 원시 응답을 얻었다. 이것만으로 시스템 지시가 전달되지 않는지, 출력 제약이 실제로 적용되는지, 또는 모델이 의미 판단을 잘못하는지 구분할 수 없다. 이번에는 **기존 `supported` 응답이 나온 같은 PC01/P014 한 쌍**에서 메커니즘 통제 두 개를 별도로 실행한다.

1. `schema_forced_unsupported`: 기존 메시지·모델 설정은 그대로 두고 `relation_status` JSON 스키마 enum만 `unsupported` 하나로 바꾼다. 출력이 `unsupported`이면 해당 서버 호출에서 스키마 제약이 관찰됐다고 해석한다. 이는 위험 관계의 진실성이나 모델의 의미 능력이 아니다.
2. `system_forced_unsupported`: 기존 스키마·사용자 메시지·모델 설정은 그대로 두고 시스템 메시지 끝에 이번 응답을 `unsupported`·2번으로 강제하는 **인위적 진단 지시**만 추가한다. 출력이 달라지면 그 지시가 이 호출의 생성에 영향을 줄 수 있음을 확인한다. 그대로여도 시스템 메시지가 전혀 전달되지 않았다고 단정하지 않는다. 기존 의미 과제와 충돌하는 지시를 따르는 능력만 관찰하기 때문이다.

독립 검증기는 두 요청 각각에서 지정한 **한 입력 요소 외 모든 JSON 필드가 v12 요청과 같은지** 확인한다. 출력 계약 유효성, 강제한 상태의 관찰 여부, 전송·길이 오류를 별도로 기록한다. 두 통제를 순서대로 각 1회 실행하고 오류에서 멈추며 재시도하지 않는다. 사전 커밋에 코드·데이터·요청 해시·토큰 수·Q5 SHA-256·컨테이너 digest를 고정한다. 원시 응답은 저장소 밖 제한 권한 폴더에, 공개 저널에는 해시와 오류만 남긴다. AWS·KT cloud는 사용하지 않는다.

이 두 단회 통제는 분산이나 일반화 성능을 추정할 수 없다. 관찰 결과만으로 기존 v12/v13 수렴의 단일 원인을 확정하지 않고, 다음 가설의 우선순위를 정하는 데 쓴다. B→A, 최종 안전 경로, 새 미노출 평가와 공식 정확도는 다루지 않는다.
