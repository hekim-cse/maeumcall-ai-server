# A/S 위험 주체 구절 객체 출력 형식 오라클 진단 설계

> 2026-11-21 실행 전 설계. 이미 사용자 검수한 PC01 한 문장에 **정답을 프롬프트로 제공하는 개발 진단**이다. 주체 추출 정확도, 안전 성능, 공식 개선율의 분모가 아니다.

## 분리할 질문

[직전 대조 진단](nlu_safety_atomic_edge_controls_v5_development_result.md)에서 PC01은 명시적 발생 위치가 있어도 현재 두 필드 스키마 아래 유효한 `unresolved`·공란을 냈다. [스키마 제거 진단](nlu_safety_atomic_edge_format_v3_development_result.md)에서는 비공란 문자열이 나오지만 구절 객체 계약이 깨졌다. 이번에는 **정답을 알 때도 비공란 구절 객체를 낼 수 있는지**부터 본다. PC01의 정답을 알려주므로 의미 선택 능력은 평가할 수 없다.

## 고정 입력과 두 오라클

- [v5 검수 사례](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-controls-v5-cases.json)의 PC01 원문·접수 제품 A·위험 사건 E·발생 상태·정답 B=`선풍기 모터`, 종류=`location`을 사용한다. 새로운 발화나 정답을 만들지 않는다. TX·GB 봉인 자료는 읽지 않는다.
- 두 조건 모두 v4 주체 단독 메시지를 시작점으로 사용하고, 동일한 두 필드 JSON 스키마·Q5 모델 파일·컨테이너 이미지·자원·생성 설정을 유지한다. `subject_span`은 `{clause_index, quote}` 객체 또는 공란, `event_subject_kind`는 기존 enum이다.
- **F1 JSON 복사:** 기존 사용자 메시지 끝에 정확한 두 필드 JSON 정답 객체를 제공하고 **같은 두 필드와 값**으로 출력하도록 요청한다. 공백이나 키 순서의 바이트 일치는 요구하지 않는다. 이는 객체 직렬화 가능성 점검이다.
- **F2 평문 조립:** 기존 사용자 메시지 끝에 `2번 문장의 선풍기 모터`와 종류 `location`을 **평문으로만** 제공하고, 이 문장 번호·구절·종류를 두 필드 객체에 담도록 요청한다. 완성된 JSON 답안은 주지 않는다. 이는 정답을 제공받은 상태의 구절 객체 조립 점검이다.
- F1→F2 순서로 각 한 번씩 모두 호출한다. F1의 성패에 따라 F2를 생략하지 않는다. 재시도·부분 실행 재개는 하지 않는다. 두 프롬프트는 요구 표현이 다르므로 단일 변수 인과 A/B 비교로 해석하지 않는다.

## 실행 전 고정과 재검증

코드·이 문서·사용할 v5 검수 입력을 먼저 커밋된 상태에서 확인한다. 원본 v5 코드·방법·프로토콜·저널·원시 응답은 바꾸지 않는다. 깨끗한 작업 트리에서 모델 SHA-256과 고정 소스·입력 해시를 확인한 뒤, **두 요청 본문 바이트의 SHA-256과 호출 순서**를 프로토콜에 기록해 모델 실행 전에 별도 커밋한다. 기존 v5 프로토콜·공개 저널의 해시도 함께 대조해 PC01 기준선의 출처를 고정한다.

실행기는 로컬 Docker 컨텍스트·소켓, 컨테이너 이미지·자원·모델 마운트와 고정 요청 해시를 확인한다. 동일 프로토콜은 다른 출력 경로를 지정해 재실행하지 못하게 한다. 공개 저널에는 호출·전송·종료 메타데이터와 응답 해시만 기록한다. 원시 응답은 저장소 밖 권한 제한 폴더에 둔다. 출력 계약 오류와 의미 결과는 독립 검증기가 원시 응답을 재생해 판정한다. 저널 전체와 검증기 SHA-256도 결과에 기록한다.

## 사전 지정 지표와 해석

조건별 전송·종료 오류, 출력 계약, 유효한 비공란 객체, 원문 인용 유효성, B 구절과 종류의 **제공한 정답과의 일치**, 두 필드 객체의 구조적 일치, 계약 유효 공란을 각각 보고한다. 오라클에서 공란은 안전한 판단 점수가 아니라 **제공된 답안 출력 과제의 실패**다. 계약 오류는 의미 정답으로 채점하지 않는다. 두 조건 모두 정답이 모델 입력에 있으므로 일치 건수를 **추출 정확도**라고 부르지 않는다. 지연은 기술 기록으로만 남기고 토큰 수는 수집하지 않는 한 추정하지 않는다.

아래 F1/F2의 **성공**은 계약을 통과하고 제공한 B 구절·종류가 모두 일치하는 두 필드 객체를 낸 경우로 고정한다. 계약 유효 비공란이지만 값이 틀린 경우는 별도 부분 신호로 보고하며 성공에 넣지 않는다.

- F1만 성공하면 객체를 복사해 낼 수 있다는 신호이며 평문 단서의 객체 조립은 실패한 것이다.
- F2만 성공해도 이 스키마에서 비공란 객체 출력이 가능하다는 신호지만, F1 복사 지시의 실패 원인은 별도로 남는다.
- 둘 다 성공하면 형식 출력과 정답 제공 시 조립은 가능하다. 직전 비오라클 PC01의 실패 원인을 **주체 선택·보류 판단 또는 프롬프트 상호작용** 쪽으로 좁히는 개발 가설이 된다. 프롬프트가 다르므로 단일 원인을 입증하지 않는다.
- 둘 다 실패하면 이 두 지시 방식에서 출력 가능성을 보이지 못한 것이다. 스키마/서버 자체가 비공란 객체를 생성할 수 없다고 단정하지 않는다.

어느 결과에서도 B→A·최종 안전 경로는 평가하지 않고 서비스에 연결하지 않는다. 다음 후보를 선택한 뒤에는 별도 개발 관문과 새 미노출 검수 평가가 필요하며, 이 오라클 수치는 그 성능 분모에 넣지 않는다.
