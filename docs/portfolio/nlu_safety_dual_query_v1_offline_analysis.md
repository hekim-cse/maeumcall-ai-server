# A/S 위험 출처 양방향 질문의 오프라인 실패 분석

> 2026-11-17. **새 모델 호출 없음.** 이미 노출된 AI 작성·사용자 검수 ES 자료와 양방향 질문 실험의 저장 기록을 다시 대조한 개발 진단이다. 공식 정확도, 개선율, 실제 서비스 성능으로 해석하지 않는다.

## 재검증 범위

- [동결 프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-dual-query-v1-development-protocol.v1.json)의 소스 24개와 입력 5개가 현재 파일과 일치하는지 확인했다. 기존 [독립 검증기](../../experiments/as_safety_dual_query_v1/verify.py)로 공개 저널·비공개 원시 응답의 순서, 파일 목록, 권한, SHA-256, 계약과 집계를 먼저 재검증했다. 프로토콜 SHA-256은 `5b97d2882c30067925a41c0421d40c09f170183b44109d2f655093303204e5d5`, 저널 SHA-256은 `93ddf25bc5ca02f259efe5f5c2b33284655918602e52997a6bee5ec8041fb270`이다.
- [오프라인 감사기](../../experiments/as_safety_dual_query_v1/offline_audit.py)는 동결 코드의 메시지 생성과 전송 payload 구성에 따라 18사건의 36개 요청 본문을 **메모리에서 재구성**하고, 비공개 원문을 출력하지 않은 채 질문·입력·응답의 동일성만 센다. 이 값은 당시 서버가 수신한 HTTP 바이트의 직접 기록이 아니다. 당시 wire 요청 본문은 보존되지 않았다.
- 당시 실험에서 검수된 접수 대상 A·사건 E·위험 주체 B·발생 상태를 두 질문에 제공했다. 정답 관계와 안전 경로는 제공하지 않았다. 따라서 이 감사도 A/E/B 추출이나 서비스 종단 간 정확도를 다루지 않는다. TX·GB 봉인 자료는 열거나 사용하지 않았다.

저장소 루트에서 아래처럼 재검증할 수 있다. `--private-dir`에는 실험 당시의 소유자 전용 원시 응답 폴더를 지정한다. 모델은 **파일 해시 확인에만** 사용되며 호출하지 않는다.

```bash
python3 -m experiments.as_safety_dual_query_v1.offline_audit \
  --protocol evals/structured_nlu/data/ai_heldout/as-safety-dual-query-v1-development-protocol.v1.json \
  --journal evals/structured_nlu/data/ai_heldout/as-safety-dual-query-v1-development-journal.v1.jsonl \
  --private-dir /path/to/owner-only-raw \
  --model-path /path/to/kanana-q5.gguf
```

## 관찰된 결과

| 오프라인 대조 | 결과 |
| --- | ---: |
| 재검증된 비공개 원시 응답 | 36/36 |
| 재구성 요청 본문 중 고유한 것 | 36/36 |
| 같은 사건에서 두 요청 본문이 동일한 쌍 | 0/18 |
| 같은 사건에서 시스템 질문 문구가 다른 쌍 | 18/18 |
| 같은 사건에서 사용자 입력 JSON이 같은 쌍 | 18/18 |
| 같은 사건에서 원시 응답 바이트가 같은 쌍 | 18/18 |

관찰된 **현재 제품 위험 8사건**과 **다른 출처 위험 9사건**은 두 질문 모두 `yes`였다. 유일한 `unknown/unknown`은 **발생이 불확실한 현재 제품 위험 1사건**이다. 이 18건에서는 각 질문의 답이 제품 소속 관계를 구분하지 못했다. `yes`가 관찰된 위험과 함께 나타난다는 것은 이 자료의 상관 패턴일 뿐, 모델이 발생 상태를 관계 대신 판단했다고 단정할 수 없다. 보수적 결합으로 관계 확정 0/18, 즉시 안전 조치 누락 8/8사건이라는 [원래 결과](nlu_safety_dual_query_v1_development_result.md)는 그대로다.

두 질문은 같은 사용자 입력과 같은 `yes / no / unknown` 출력 스키마를 사용하지만 시스템 메시지 끝의 질문 문장은 다르다. 온도 0, seed 0, `yes`가 첫 enum 값인 설정도 같다. **Python에서 같은 질문을 두 번 만든 흔적은 없다.** 다만 저장된 응답만으로 서버의 시스템 메시지 처리, 첫 선택지 편향, 긍정 응답 편향, 질문 위치의 효과 또는 모델의 관계 추론 능력 중 어느 것이 원인인지 확정할 수 없다. `yes`가 첫 enum인 점은 반증할 가설이며 확인된 원인이 아니다.

같은 Q5의 앞선 [관계 정의 순서 진단](nlu_safety_relation_oracle_order_v1_result.md)은 정의 순서만 바꿔도 12/18사건의 관계 답이 달라졌다. [근거 그래프 진단](nlu_safety_evidence_graph_v1_development_result.md)은 E→B와 B→A 연결 종류를 19건 모두 같은 값으로 출력했고 계약 통과가 4/19였다. 이 결과들은 출력 선택과 복합 계약의 취약성을 **의심할 근거**지만, 실험 조건과 출력 계약이 달라 이번 양방향 실패의 인과 원인이나 점수 개선율을 계산하는 비교군은 아니다.

## 다음 관계 판단 설계

1. **근거 유형을 먼저 정의한다.** 검수된 A·E·B와 원문에 대해 B가 A와 동일한지, A의 부품·위치인지, A를 가리키는 지시어인지, 명시적으로 다른 물건인지, 근거가 부족하거나 충돌하는지를 구분한다. 원문 근거 구절과 문장 위치를 함께 보존한다. 위험의 발생 여부는 관계와 별도 축으로 둔다.
2. **명시적인 근거만 관계로 확정한다.** 동일 대상·검증된 소속·해결된 지시어이면 `current`, 명시적으로 별개이면 `other`, 불명확·충돌이면 `unknown`을 제안한다. 이 규칙과 우선순위는 사례별 근거 라벨을 보기 전에 고정해야 한다. ES 자료로 수정한 후보는 개발 진단으로만 취급한다.
3. **안전 경로를 별도 관문으로 평가한다.** `unknown` 보류가 관찰된 현재 위험을 즉시 조치하지 못하면 그 사건 수와 사례 수를 따로 보고하고 서비스에 연결하지 않는다. 관계 정답률만 높거나 오경고만 줄어도 안전 관문을 통과한 것으로 보지 않는다. 현재 서비스 안전 가드는 유지한다.
4. **모델 실험은 반증할 가설이 생긴 뒤에만 한다.** 예를 들어 enum 순서 또는 질문 위치의 효과를 확인하려면 한 변수만 바꾸고 동일한 노출 개발 사건에서 사전 고정한 비교를 해야 한다. 그 결과도 공식 개선율은 아니다. 후보가 개발 관문을 통과할 때 새 미노출 사례의 발화·근거·관계·경로를 사용자 검수 후 동결해 별도 평가한다.

이번 문서는 새 관계 후보의 성능을 주장하지 않는다. 다음 작업은 ES 18사건의 **원문 근거 유형 초안**을 만들고 사람이 검수할 수 있게 정리하는 것이다.
