# A/S 안전 근거 축약 후보 개발 계획

## 근거와 가설

기존 네 번호 계약의 별도 진단에서는 RE·V 32건 중 26건이 사건 번호 또는 발생 번호의 누락, 2건이 접수 제품 번호의 누락으로 실패했다. 출력 스키마는 `null`을 허용하지만 검증기는 사건이 있으면 해당 번호를 필수로 요구했다. 어느 번호가 비었는지와 모델이 비운 이유는 기록에서 알 수 없다.

새 개발 후보는 같은 위험 사건에 요구했던 `event_index`와 `occurrence_index`를 하나의 위험 근거 번호로 합친다. 접수 제품 근거와 출처·정정 근거는 따로 둬 V06의 다른 제품 출처와 V09의 뒤 문장 출처 불명을 표현한다. 모델이 선택하지 않은 번호를 서버가 임의로 채우지 않는다. 근거가 없거나 모순되면 계약 오류로 남긴다. 한 번의 호출로 기존 후보와 비교해 호출 수·지연 증가를 제한한다.

## 사전 선택 기준

이미 노출된 AI 작성·사용자 검수 RE01–RE16과 V01–V16에서만 기준선과 새 후보를 고정 조건으로 비교한다. V의 현재 제품 실제 위험 즉시 보호는 기준선 7/8 이상, 다른 출처 위험의 즉시 보호 오분기는 기준선 1/4 미만이어야 한다. V06은 일반 수집, V09는 안전 확인, V07·V12는 즉시 보호여야 한다. 후보 계약 오류는 기준선보다 많지 않아야 한다. RE의 안전 확인 누락과 각 방식의 지연 중앙값·p90도 별도로 보고한다. 하나라도 필수 조건에 실패하면 후보를 기각한다.

코드·입력·모델·요청 설정·검증기 해시를 첫 호출 전에 커밋한다. 원문 응답은 저널에 보존하지 않고 중단·오류를 재시도하지 않는다. 작은 노출 개발 집합의 통과는 일반화나 공식 정확도를 뜻하지 않는다. [TX01–TX16](nlu_safety_transfer_fresh_field_review.md)은 후보가 개발 기준을 모두 통과하고 고정되기 전에는 모델에 보내지 않는다.
