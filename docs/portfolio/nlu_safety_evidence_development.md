# A/S 안전 근거 분리 개발 진단

## 설계 판단

기존의 명시적 규칙은 위험 단어가 다른 물건에 붙은 CF24를 현재 A/S 제품의 위험으로 잘못 처리했다. 앞선 안전 확인 후보는 모호한 발화 8건을 모두 일반 수집으로 보내고, 실제 위험 12건 중 10건을 즉시 대응 대신 확인 질문으로 보냈다. 위험 키워드 탐지만 늘리면 대상과 발화 태도의 오류를 분리해 검증하기 어렵다.

이번에는 **위험 근거 원문, 위험 대상, 발화 태도**를 각각 구조화하는 개발용 프로브를 만든다. 모델이 제시한 근거 문구가 사용자 발화의 연속 문자열인지 서버가 검증한다. 서버는 `현재 제품 + 실제 관찰`만 즉시 대응, `현재 제품/대상 불명 + 불확실한 관찰`은 확인, 다른 제품·부정·가정은 일반 경로로 매핑한다. 근거 문구의 포함 여부만 기계적으로 확인할 수 있고, 대상·태도의 의미 판단은 여전히 모델에 의존한다.

이 프로브는 서비스 그래프에 연결하지 않았다. 추가 모델 호출이 필요하므로 지연과 요청 횟수를 함께 살펴야 한다. [CF01–CF32](nlu_safety_confirmation_fresh_review.md)는 이미 두 차례 모델에 노출됐고 코드 작성자도 정답을 봤다. 따라서 이번 결과는 **개발 진단**이며 새 정확도나 개선율이 아니다. 우선 출력 계약 준수, 근거 환각, 대상·태도 혼동을 확인하고, 서비스 후보 채택 여부를 그 뒤 판단한다.

## 첫 진단: 프롬프트 지시만 사용

커밋 `5b8bb34`의 프로브를 같은 로컬 Q5에 CF01–CF32 각 한 번씩 실행했다. [진단 결과](../../evals/structured_nlu/data/ai_heldout/nlu-safety-evidence-exposed-development.v1.json)는 **32/32건 JSON 파싱 실패**였다. 임시 확인한 한 응답은 값 이름을 적었으나 JSON 객체가 아닌 줄 단위 텍스트였다. 이 경우 대상·태도 판단의 정확도를 계산할 수 없다. 모델 서버가 지원하는 JSON Schema 제약 출력을 다음 개발 후보로 확인한다.

[llama.cpp 서버 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md)는 Chat Completions의 `response_format`으로 JSON 객체와 스키마 제약을 지원한다. 같은 사례 한 건을 시험했을 때 `json_schema` 형식은 기존 줄 단위 응답을 바꾸지 못했으나, `json_object`와 스키마 조합은 JSON 객체를 반환했다. 이 응답의 근거 문구는 원문을 어미까지 정확히 복사하지 않아 출처 검증에서 거부됐다. 따라서 형식 강제와 근거 정확성을 별개로 측정한다.

## 두 번째 진단: JSON 객체 제약

커밋 `e8970c9`의 스키마 제약 프로브를 노출된 CF01–CF32에 한 번씩 실행했다. [결과](../../evals/structured_nlu/data/ai_heldout/nlu-safety-evidence-exposed-development.v2.json)에서 32건 모두 JSON 파싱은 통과했지만, 근거·대상·태도의 서버 계약까지 통과한 건 **10/32건**이다. 통과한 10건 중 즉시 위험 대응 분류는 9건이었다. 그중 실제 위험 구간은 3건, 모호한 구간은 3건, 현재 제품의 위험 진술이 없는 구간은 3건이었다. 나머지 1건은 일반 수집으로 분류됐다. 검증 실패 22건은 `ValueError`로 기록됐고, 개별 실패 내용은 결과 파일에 저장하지 않았다.

따라서 JSON 형식 제약만으로 신뢰할 수 있는 안전 판단이 되지 않는다. 특히 모호한 발화를 직접 위험으로 확정하는 전이가 나타나 이 후보도 서비스에 연결하지 않는다. 다음 개발 진단은 모델이 근거 문구를 생성하지 않고, 서버가 원문에서 나눈 구간의 번호를 선택하게 한다. 구간 번호는 출처를 보장하지만 대상·태도 판단의 정확성까지 보장하지는 않는다.

## 세 번째 진단 설계: 원문 구간 번호

서버가 발화를 문장 경계에서 나누고 1부터 번호를 붙인다. 모델은 스키마에서 허용한 번호 또는 공란만 고른다. 이렇게 하면 모델이 원문을 바꿔 쓰는 문제는 구조적으로 줄어든다. 대신 문장 구분이 부정확하거나 여러 문장 사이의 대상 관계를 모델이 틀리게 이해할 수 있다. 대상·태도 분류 오류가 남는다면 이 방법도 서비스 경로에 적용하지 않는다.

## 후속 검증 조건

서비스에 연결할 후보가 정해지면 먼저 코드와 요청 설정을 고정한다. 이후 AI 작성 새 발화의 문장·행동·전체 필드·기대 상태를 사용자 검수로 확정하고, 모델 호출 전에 입력과 프로토콜을 커밋한다. 직접 위험 대응, 불확실성 확인, 비위험 일반 진행, 모델 오류, 추가 요청과 지연을 별도 분모로 보고한다.
