# A/S 안전 근거 분리 개발 진단

## 설계 판단

기존의 명시적 규칙은 위험 단어가 다른 물건에 붙은 CF24를 현재 A/S 제품의 위험으로 잘못 처리했다. 앞선 안전 확인 후보는 모호한 발화 8건을 모두 일반 수집으로 보내고, 실제 위험 12건 중 10건을 즉시 대응 대신 확인 질문으로 보냈다. 위험 키워드 탐지만 늘리면 대상과 발화 태도의 오류를 분리해 검증하기 어렵다.

이번에는 **위험 근거 원문, 위험 대상, 발화 태도**를 각각 구조화하는 개발용 프로브를 만든다. 모델이 제시한 근거 문구가 사용자 발화의 연속 문자열인지 서버가 검증한다. 서버는 `현재 제품 + 실제 관찰`만 즉시 대응, `현재 제품/대상 불명 + 불확실한 관찰`은 확인, 다른 제품·부정·가정은 일반 경로로 매핑한다. 근거 문구의 포함 여부만 기계적으로 확인할 수 있고, 대상·태도의 의미 판단은 여전히 모델에 의존한다.

이 프로브는 서비스 그래프에 연결하지 않았다. 추가 모델 호출이 필요하므로 지연과 요청 횟수를 함께 살펴야 한다. [CF01–CF32](nlu_safety_confirmation_fresh_review.md)는 이미 두 차례 모델에 노출됐고 코드 작성자도 정답을 봤다. 따라서 이번 결과는 **개발 진단**이며 새 정확도나 개선율이 아니다. 우선 출력 계약 준수, 근거 환각, 대상·태도 혼동을 확인하고, 서비스 후보 채택 여부를 그 뒤 판단한다.

## 첫 진단: 프롬프트 지시만 사용

커밋 `5b8bb34`의 프로브를 같은 로컬 Q5에 CF01–CF32 각 한 번씩 실행했다. [진단 결과](../../evals/structured_nlu/data/ai_heldout/nlu-safety-evidence-exposed-development.v1.json)는 **32/32건 JSON 파싱 실패**였다. 임시 확인한 한 응답은 값 이름을 적었으나 JSON 객체가 아닌 줄 단위 텍스트였다. 이 경우 대상·태도 판단의 정확도를 계산할 수 없다. 모델 서버가 지원하는 JSON Schema 제약 출력을 다음 개발 후보로 확인한다.

## 후속 검증 조건

서비스에 연결할 후보가 정해지면 먼저 코드와 요청 설정을 고정한다. 이후 AI 작성 새 발화의 문장·행동·전체 필드·기대 상태를 사용자 검수로 확정하고, 모델 호출 전에 입력과 프로토콜을 커밋한다. 직접 위험 대응, 불확실성 확인, 비위험 일반 진행, 모델 오류, 추가 요청과 지연을 별도 분모로 보고한다.
