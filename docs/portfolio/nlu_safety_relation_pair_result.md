# A/S 제품과 위험 사건 관계 후보: 새 발화 쌍 비교

## 평가 경계

- 2026-11-09에 사용자가 문장·경로와 모든 근거 번호·상태를 탐색용으로 검수한 AI 작성 RE01–RE16을 사용했다. 사람 작성 독립 사례나 공식 정확도 평가가 아니다.
- 사례와 정답, 비교기, 검증기, 모델·요청 설정의 SHA-256을 첫 모델 호출 전에 [프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-relation-pair-protocol.v1.json)로 커밋했다. 동일한 Kanana Q5 파일(SHA-256 `644b04cd…f3d`)을 CPU 2개·메모리 4 GiB·고정 컨테이너에서 사용했다. 각 사례에 기존 단일 근거 방식과 새 제품·위험 이중 근거 방식을 교대로 호출했다. 실패는 재시도하지 않고 오류로 센다.
- [원자료](../../evals/structured_nlu/data/ai_heldout/as-safety-relation-pair-result.v1.json)는 발화와 모델 출력 전문을 저장하지 않는다. 독립 [검증기](../../scripts/verify_as_safety_relation_pair.py)가 사례 순서, 판단값 범위, 경로, 집계를 다시 계산해 통과했다.
- 코드 리뷰 후 검증기에 문장 수·정답 경로·라우터 소스 해시·유한한 지연 시간 확인을 추가해 같은 원자료를 다시 검증했다. 실행 당시 검증기의 해시는 프로토콜에 남아 있고, 실행기·모델·데이터·결과는 변경하지 않았다.

관계 후보의 세부 필드 일치는 `product_index` 13/16, `hazard_index` 13/16, `target_relation` 8/16, `event_status` 10/16이고 네 필드 완전 일치는 5/16이다. 근거 번호를 맞혀도 위험이 현재 접수 제품에 속하는지 판단하는 단계에서 실패했다. 특히 RE09·11·12는 다른 출처의 위험을 현재 제품의 실제 위험으로 판단했다. RE13은 `ValueError`로 기록됐다. 서버 응답 해석 단계와 관계 필드 검증 단계가 구분되지 않아 정확한 원인은 확인되지 않았다.

현재 후보는 전체 경로 일치가 낮고, 다른 출처 위험을 현재 제품의 위험으로 오분기하는 문제가 크다. **서비스 그래프에 연결하지 않는다.** 이 결과를 개선율이나 안전성 입증으로 쓰지 않는다. 작은 표적 사례에서의 실패 원인 분석이다. 잘린 HTTP 응답은 현재 고정 실행기의 예외 범위 밖이므로 이 결과만으로 그런 장애에 대한 완주를 보장하지 않는다. 다음 실행기는 응답 단계와 검증 단계를 구분하고 잘린 응답을 오류로 기록해야 한다. 다음 후보는 더 많은 규칙을 덧붙이기 전에 두 문장 사이의 소유·지시 관계 판단을 분리해서 검증하고, 새로 작성·검수한 사례로 다시 평가해야 한다. 실제 위험 보고 뒤 수리 가능 여부를 묻는 발화도 새 검수 사례에 포함해야 한다.
