# A/S 위험 주체 전건 보류 원인 분리 개발 실험

> 2026-11-20 설계. 모델 실행 전 문서다. ES 발화는 AI 작성·사용자 검수 후 이미 노출된 개발 자료이므로 이 비교를 공식 정확도나 개선율로 사용하지 않는다.

## 왜 이 비교를 하는가

[첫 E→B 진단](nlu_safety_atomic_edge_v1_development_result.md)은 19건 모두 출력 계약을 통과했지만, 원시 응답이 전부 동일한 `unresolved`·두 구절 공란이었다. 비공란 B 정답 18건은 0건 추출됐다. 이는 보류 지시 문구, 세 필드 동시 추출, 출력 스키마 또는 모델의 판단 중 어느 것이 원인인지 특정하지 않는다. 이번에는 **보류 판단 문장 한 곳의 영향만** 확인한다.

## 고정 조건과 단일 변경

- 대상은 기노출 ES01·ES03·ES09·ES17·ES18의 첫 사건 5건이다. ES01/ES09는 같은 연기 사건의 현재 제품/다른 제품 출처 대비, ES03은 명시 주체, ES17은 실제 출처 불명, ES18은 발생 상태가 불확실하지만 위치가 명시된 사례다. ES에는 E→B `implicit` 검수 라벨이 없으므로 이 비교에 암시 연결 대조군이 있다고 주장하지 않는다.
- 각 사건에 원래 문구 조건 A와 수정 문구 조건 B를 한 번씩 적용한다. 순서를 사전에 고정하고 A→B와 B→A를 섞는다. 재시도와 사후 사례 교체는 하지 않는다.
- A는 첫 진단의 시스템·사용자 메시지와 동일하다. B는 사용자 메시지의 **한 문장만** 바꾼다.
  - A: `주체를 확인할 수 없으면 unresolved와 두 구절 모두 null을 반환하세요.`
  - B: `원문에 E와 직접 연결되는 주체·위치 구절이 있으면 해당 구절을 인용하세요. 연결할 구절이 확인되지 않을 때만 unresolved와 두 null을 반환하세요.`
- 그 밖의 원문, 검수된 A·E·발생 상태, 세 필드 JSON 스키마, Kanana Q5 모델 파일, 컨테이너 이미지, CPU·메모리·컨텍스트 설정, temperature·seed·토큰 한도·타임아웃을 같게 둔다. 검수 B·관계·근거 정답·기대 안전 경로는 모델 입력에서 제외하고 채점에만 사용한다.
- 코드·입력·순서·정확한 요청 해시·모델·이미지·설정을 호출 전에 프로토콜로 고정한다. 원시 응답은 저장소 밖 소유자 전용 파일에 보관하고 공개 저널에는 원문과 응답을 넣지 않는다. 중단 시 부분 기록을 덮어쓰거나 이어서 재시도하지 않는다.

## 비교 지표와 해석 경계

조건별로 호출/전송 오류, 출력 계약, `unresolved` 비율, 비공란 B 인용 일치(4건), E→B 종류·근거 일치(각 5건), **비공란 E→B 근거 일치(4건)**, ES17의 올바른 공란과 잘못된 주체 확정을 분리한다. ES18의 불확실한 **위험 발생**과 명시된 **위치**도 구분한다. 원본 첫 진단의 수치는 참고로 두되, 이번 5건은 같은 실행 환경에서 A와 B를 새로 짝지어 비교한다. 새 A 출력이 보관된 첫 진단의 같은 5건과 일치하는지도 별도로 확인한다. 일치하지 않으면 원래 전건 보류의 원인에 대한 해석을 유보하고, 같은 실행 안의 A/B 차이만 보고한다.

이 소수 개발 비교는 인과 가설을 좁히는 진단이다. B가 일부 구절을 찾더라도 ES17에서 근거 없이 주체를 확정하면 후보로 채택하지 않는다. 둘 다 전건 보류라면 다음에는 출력 스키마와 근거 동시 요구를 **각각 별도 변수로** 시험한다. A/B 차이가 나더라도 이 5건만으로 원인을 확정하거나 19건 전체로 일반화하지 않는다. 어느 경우에도 이 차이를 공식 전체 정확도 개선율이나 안전 경로 성능으로 쓰지 않는다.

기존 개발 관문은 19건 전체에서 계약 오류 0, B 18/18, ES17 공란 1/1, E→B 종류 19/19다. 소수 비교로 이 관문을 대체하지 않는다. B→A와 서비스 안전 분기는 연결하지 않으며 TX·GB 봉인 자료는 사용하지 않는다. 후보 선택 뒤 새 미노출 발화와 정답을 실행 전에 별도 검수해 평가한다.
