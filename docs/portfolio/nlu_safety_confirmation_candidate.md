# A/S 안전 확인 상태 후보

## 근거와 목표

[PF 후속 평가](nlu_safety_postfreeze_run_log.md)에서 이전 코드와 확장 정규식 후보 모두 실제 위험 2/8만 안전 상태로 보냈다. 두 코드에서 놓친 여섯 건의 구조화 모델 `safety_status`는 모두 공란이었다. 기존 규칙에 위험 단어를 더하는 방식은 새 사례에서 개선되지 않아 철회했다.

이 문서는 **후보 구현의 설계와 검증 계획**이다. 새 성능 수치나 배포 완료를 주장하지 않는다. 앞서 노출된 PF에서 안전 전용 질문은 위험 8건을 모두 `true`로 답했지만, 비위험 8건 중 정답 4건·오탐 1건·형식 오류 3건이었다. 따라서 그 판단을 곧바로 위험 확정이나 차단에 쓰지 않는다. 현재 후보는 형식 실패에 한 번 재시도하지만 이 변경의 실모델 결과는 아직 없다.

## 상태 계약

| 입력 | 후보의 처리 |
| --- | --- |
| 기존의 명백한 위험 표현 | 모델보다 먼저 `safety_action_required`로 진입 |
| 위험 단서가 있는 발화 | 짧은 안전 전용 질문을 실행. `true` 또는 두 번의 형식 실패·모델 오류이면 `confirming_safety_status`에서 실제 발생 여부를 질문 |
| 안전 전용 질문이 `false` | 기존 구조화 추출과 일반 A/S 상태 전이 계속 |
| 확인 상태에서 명시적 긍정·실제 위험 표현 | `safety_status=safety_issue`, 보호 상태 진입 |
| 확인 상태에서 명시적 부정 | `safety_status=no_safety_issue`, 정보 수집 또는 전체 확인으로 복귀 |
| 확인 상태에서 불분명한 답 | 확인 상태 유지. 모델이 답의 의미를 추측하지 않음 |
| 확인 상태에서 통화 종료 | 기존 종료 경로 진입 |

확인 상태에서는 일반 접수를 중단하지만 안전 이상을 확정하지 않는다. 확인 질문 이전의 발화에서 새 업무 필드는 추출하지 않으므로, 안전 이상을 부정한 뒤에는 필요한 제품·증상 정보를 다시 말해야 할 수 있다. 이는 위험 판단을 일반 업무 추출보다 먼저 처리하는 데 따른 사용성 비용이다.

## 남은 검증

- 현재 단어 기반 선별은 위험 확정기가 아니다. 노출된 PF에서는 명백한 위험 우회와 선별 조건을 합쳐 위험 8/8을 검사 대상으로 잡지만, 비위험 8/8도 안전 전용 질문 대상이다. 선별의 실제 사용자 분포와 추가 지연은 알 수 없다.
- 확인 질문 빈도, 실제 위험 보호 진입, 비위험 대화 중단, 잘못된 위험 확정, 형식 재시도·오류, 턴별 지연을 **같은 새 사례**에서 기록해야 한다.
- AI 작성 사례를 사용자에게 문장·행동·전체 필드·안전 방향까지 검수받고, 사례·정답·요청 정책을 모델 호출 전에 고정한다. AI 작성·1인 검수 결과는 표적 탐색 평가로만 표기한다.
- 기존 PF·SC·CX는 개발·회귀 사례로만 사용한다. 이 후보를 운영 코드에 병합할지는 새 사례의 위험 누락과 비위험 확인 질문 비용을 함께 확인한 뒤 판단한다.
