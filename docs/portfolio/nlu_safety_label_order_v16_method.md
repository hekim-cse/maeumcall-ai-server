# A/S 후보 관계 상태 설명 순서 통제

> 2026-11-24. 이미 모델에 노출된 PC01·NC01의 사용자 검수 후보 네 쌍으로 **첫 선택지 편향 가능성**을 살피는 개발 진단이다. 공식 정확도·개선율이나 최종 안전 경로 평가가 아니다.

## 문제와 한 가지 변경

[v12](nlu_safety_eb_pair_relation_v12_development_result.md)와 [v13](nlu_safety_eb_criteria_v13_development_result.md)은 후보 구절과 시스템 판단 기준이 달라도 네 쌍 모두 `supported`·2번을 냈다. [템플릿 점검](nlu_safety_chat_template_audit.md)은 시스템 지시가 서버의 렌더링 경로에 들어감을 확인했다. v12 사용자 메시지는 세 상태를 `supported → unsupported → insufficient` 순서로 설명한다. 같은 출력이 **맨 앞 상태로의 수렴**인지 확인하려면 설명 순서만 바꾸는 것이 한 번에 여러 프롬프트 요소를 바꾸는 것보다 해석이 좁다.

기존 메시지에서 상태와 그 괄호 속 정의의 **순서만** `insufficient → unsupported → supported`로 뒤집는다. 정의 문구, 나머지 시스템·사용자 내용, 네 원문과 후보 ID·구절, JSON 스키마, Q5 모델 파일, 서버 이미지, 생성 설정과 호출 순서는 v12와 동일하게 둔다. 검수 상태·근거 번호는 모델 입력에 추가하지 않는다. 기존 원시 응답과 새 응답은 저장소 밖에 두고 해시와 계약·판정 결과만 공개한다.

## 사전 판정

- 네 후보의 요청 바이트와 변경 전후 JSON 차이를 생성 전에 고정한다. 실제 입력 토큰 수를 확인해 컨텍스트 초과 가능성을 배제한다.
- 네 쌍을 v12와 같은 순서로 각 한 번 호출하고 재시도하지 않는다. 전송 오류, 길이 종료, JSON·교차 필드 계약 오류가 나면 그 행을 기록하고 즉시 멈춘다.
- 각 쌍의 계약 통과, 상태·근거 번호, v12 대비 전이, 원시 응답 해시 일치 여부를 분리 보고한다. 네 쌍 모두 끝났을 때만 `supported` 상수 응답이 유지됐는지 계산한다.
- 새 결과가 `insufficient`로 일괄 바뀌면 **설명 순서 민감성**을 지지하는 근거가 된다. 후보에 맞게 서로 다른 상태로 바뀌면 현재 선택지 순서가 구별을 방해했을 가능성이 생긴다. 변화가 없다면 이번 단회 조건에서 순서의 영향이 관찰되지 않았다고만 기록한다. 어느 결과도 모델 이해·스키마·캐시 중 단일 원인을 확정하지 못하며, 단회·기노출 자료라 정확도 일반화는 하지 않는다.

실행기는 코드·검수 입력·모델·이미지 해시, 요청 순서와 오류 중단 규칙을 별도 프로토콜로 커밋한 뒤에만 호출한다. Docker 엔진이 확인되지 않으면 준비 단계까지만 진행한다. AWS·KT cloud를 사용하지 않는다.
