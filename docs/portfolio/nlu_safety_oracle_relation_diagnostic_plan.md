# A/S 접수 대상·위험 사건 고정 관계 진단 계획

## 확인할 원인

앞선 [두 단계 개발 비교](nlu_safety_staged_development_result.md)에서는 기준선 19/32건에 비해 후보가 12/32건만 기대 경로와 일치했다. 후보는 위험 사건의 발생을 `observed`로 골라도 위험 근거 번호나 접수 대상 문장을 잘못 고를 수 있었다. 따라서 여러 필드를 동시에 생성하는 비교만으로는 **근거 선택 오류**와 **출처 관계 판단 오류**를 분리할 수 없다.

이번에는 이미 노출된 AI 작성·사용자 1인 검수 RE01–RE16, V01–V16의 기존 정답에서 접수 대상 문장 번호, 위험 사건 문장 번호, 발생 상태를 제공한다. 별도 검수한 원문 연속 구간인 접수 제품명과 위험 사건 구간도 제공한다. 모델에는 둘 사이의 관계 `current`·`other`·`unknown` 하나만 묻는다. 이 입력은 정답 일부를 제공하는 **오라클 조건**이다. 이 결과는 서비스 후보의 전체 경로 성능이나 정확도 개선율이 될 수 없다. V04에 대해서는 사용자가 이번 진단에서 접수 대상을 토스터로 지정했으므로 기존 데이터의 `other`를 소급 수정하지 않고 별도 버전의 `current` 해석을 기록한다. 과거 V04 결과와 직접 비교하지 않는다.

발생 상태가 `observed` 또는 `uncertain`인 24건만 관계 모델을 호출한다. `nonoccurring` 8건은 호출하지 않으며, 관계 정확도의 분모에도 넣지 않는다. 이번 진단에서 V04를 새 해석으로 지정하면 정답 관계는 `current` 16건, `other` 6건, `unknown` 2건이다. 기존 데이터는 바꾸지 않는다. 대상·사건 원문 구간은 모델 호출 전에 사용자가 검수한 입력으로 별도 고정하고, 각 구간이 지정 문장에 실제로 한 번 포함되는지 검사한다.

## 기록과 판단 기준

같은 Kanana Q5 모델과 로컬 실행 조건에서 24건을 ID 순서로 각 한 번만 호출한다. 호출 시작·종료를 원문 없이 기록하고, 중단 시 재시도하지 않는다. 사전 프로토콜에는 사례·구간 입력, 모델, 프롬프트·스키마·실행기·검증기, 요청 정책과 컨테이너의 해시를 고정한다. 응답의 유한 관계값, 오류 단계·예외 유형·숫자 HTTP 상태코드(있는 경우), 종료 이유와 지연만 보존한다. 독립 검증기는 49행 저널의 순서, 해시, 구간 포함, 값·오류, 정답 분모를 다시 확인한다.

관계 `current` 16건, `other` 6건, `unknown` 2건 각각의 일치 수와 계약·HTTP 오류를 별도로 보고한다. V01/02, V05/06, V07/08의 대비쌍에서 위험 출처가 바뀔 때 판단이 뒤집히는지 본다. V03/04는 사용자가 이번 진단에서 서로 다른 접수 대상을 지정했으므로 동일 대상의 출처 대비쌍이 아니며 따로 보고한다. 첫 문장이 복수 대상으로 읽힐 수 있어 전체 24건과 이 두 사례를 뺀 22건의 결과도 함께 보고한다.

**다음 구현 탐색을 위한 엄격한 기준**은 `current` 최소 15/16, `other` 6/6, `unknown` 2/2, 오류 0/24다. 이 기준은 안전 위험의 누락과 다른 제품 위험의 오분기를 동시에 피하려는 작은 개발 집합의 설계 기준이지 통계적 신뢰도나 서비스 채택 기준은 아니다. 실패하면 관계 판단 자체 또는 입력 표현을 다시 분석한다. 통과해도 접수 대상과 위험 사건을 실제 서비스 입력에서 정답 없이 식별하는 방법을 별도로 개발해야 한다. **TX01–TX16과 서비스 그래프에는 이번 오라클 조건을 사용하지 않는다.**
