# A/S 후보 관계 진단의 채팅 형식 점검

> 2026-11-24. [v12 후보 관계 진단](nlu_safety_eb_pair_relation_v12_development_result.md)과 [v15 시스템 지시 통제](nlu_safety_system_control_v15_result.md)의 입력 경로를 확인한 **읽기 전용 개발 점검**이다. 모델 생성, 정확도 평가, 서비스 코드 변경은 하지 않았다.

## 확인 방법

- v12·v15에서 고정한 Kanana Q5 GGUF 파일의 SHA-256 `644b04cde835d486df33c6d4d7552ba367fcb28802fe39b6b4bb9c60b9ab6f3d`를 다시 확인했다. GGUF 메타데이터에는 `tokenizer.chat_template`가 있고, 이 템플릿에는 `system`과 `user` 메시지를 각 역할 헤더로 렌더링하는 분기가 있다.
- 기존 이미지 digest `sha256:17155a3ce4cc906728ec99a2814bf0b4eaffaf3b4872bad8c3affed310cdbc35`와 서버 인자를 그대로 사용했다. 서버의 `POST /apply-template`에 v12 PC01/P014의 메시지와 v15에서 시스템 지시만 바꾼 메시지를 각각 전달했다. 이 API는 대화 형식을 렌더링할 뿐 추론을 실행하지 않는다. [llama.cpp 서버 문서](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-apply-template-apply-chat-template-to-a-conversation)도 이 용도를 명시한다.
- 전체 프롬프트와 원문은 공개 기록에 남기지 않았다. 렌더링 결과의 해시, 길이, 역할 헤더 개수, 원래 메시지 포함 여부만 확인했다. 점검 뒤 컨테이너를 제거하고 Docker Desktop을 종료했다.

## 관찰

| 항목 | v12 PC01/P014 | v15 시스템 지시 통제 |
| --- | ---: | ---: |
| 렌더링 문자 수 | 812 | 915 |
| `system` 역할 헤더 | 2개 | 2개 |
| `user` 역할 헤더 | 1개 | 1개 |
| 요청한 시스템 메시지 포함 | 예 | 예 |
| 추가 지시문 출현 | 0회 | 1회 |
| 렌더링 프롬프트 SHA-256 | `8d5f62c3a0612e48f63b5eb58febb22edbb363c131d629ccb3b00e501c07c9a2` | `eb2ad47893358a35d3c241413107aa3ef57def4843c8de5fe6e54986188d07bd` |

두 조건의 사용자 메시지는 같고, 렌더링된 사용자 헤더부터 끝까지도 같다. 두 `system` 헤더 중 하나는 GGUF 템플릿의 기본 시스템 구간이고 다른 하나는 요청 메시지다. v15의 추가 지시문은 요청의 시스템 구간에서 한 번 나타났다.

## 판단 범위와 다음 검증

이 점검은 **서버의 템플릿 변환 경로에 시스템 지시가 전달됨**을 보여 준다. 따라서 v15 출력이 바뀌지 않은 이유를 단순히 “시스템 메시지가 전송되지 않았다”로 설명하는 것은 현재 증거와 맞지 않는다. 다만 `/apply-template`는 `response_format`에 따른 생성 제약과 실제 모델 내부의 지시 가중치를 측정하지 않는다. v15는 의미 과제와 충돌하는 인위적 단회 지시이므로, 이 결과로 모델의 일반적인 시스템 지시 준수율을 판단할 수도 없다.

다음 모델 진단은 같은 후보 쌍에서 **의미 정답과 출력 계약이 모두 유효한 조건**을 먼저 설계해야 한다. 후보 구절·근거 문장·관계 상태를 분리해, 출력 형식 변화와 관계 판단 변화를 각각 관찰한다. 새 호출 전에 입력·모델·이미지·요청 설정·중단 조건을 고정하고, 기노출 개발 자료의 결과를 공식 정확도와 분리한다.
