# A/S 위험 출처 명시 근거 기준 규칙: 사전 설계

> 개발용 **제한적 결정론 기준선**. 모델 호출 없이 검수된 ES 원문·A·E·B 오라클을 사용한다. 검수 근거 유형표와 관계 정답은 예측 함수의 입력이 아니다. 실제 서비스 후보나 공식 정확도 개선 실험으로 간주하지 않는다.

## 목적과 가설

양방향 Q5 질문은 18/18사건을 보류했다. 새 모델을 평가하기 전에, 원문에 **직접 적힌 소속·별개 신호만** 읽는 규칙이 어디까지 관계를 확정하고 어떤 현재 제품 위험을 놓치는지 확인한다. 좁은 규칙의 낮은 포괄률은 실패가 아니라, 향후 관계 근거 추출에 필요한 범위를 드러내는 기준이다. 높은 점수가 나와도 ES가 이미 노출된 개발 자료이고 A/E/B가 정답으로 제공됐으므로 일반화나 종단 간 안전성을 입증하지 않는다.

## 고정할 예측 계약

입력은 사용자 원문, 절 번호와 원문 구절로 고정된 접수 대상 A·위험 사건 E·위험 주체 B(없을 수 있음), 독립적으로 검수된 발생 상태뿐이다. A/E/B 구절이 실제 원문의 해당 절에 존재하는지 검증한다. 이는 인용 위치 검증이며 **E가 B에서 발생했다는 의미 검증은 아니다.** 예측 함수는 `owner_to_target`, 기대 안전 경로, 검수한 근거 유형, ES 식별자를 받거나 읽지 않는다.

사전 규칙은 아래처럼 보수적으로 한정한다.

1. B가 없거나, B 또는 B 바로 앞 문맥에 `다른`·`별도`·`별개` 같은 충돌 표시가 있으면 `unknown`이다. B 안의 독립된 `옆`·`근처`·`함께`·`전용`도 보류 신호다. 다만 아래 3번의 명시적 별개 표현은 우선한다.
2. B 자체가 A와 정확히 같거나, B의 선두에 A의 **완전한 제품명**이 공백 또는 `의` 뒤의 표현과 함께 등장하고 충돌 신호가 없으면 `current`다. `A 용`처럼 용도만 나타내는 표현은 보류한다. 이는 문자열 기준의 명시 소속 **후보**이며 부품 관계의 의미가 증명된 것은 아니다. 축약 호칭·지시어·앞선 문맥의 부위는 여기서 확정하지 않는다.
3. B가 정확히 `다른 기기`이거나 `다른 기기의 ...`로 시작하고 A의 이름이 B에 없으면 `other`다. 다른 제품 이름처럼 보인다는 이유만으로는 확정하지 않는다.
4. 나머지는 전부 `unknown`이다. 출력은 관계와 결정 근거 종류만 반환하며 원문에 없는 인용이나 모델 생성 근거는 만들지 않는다.

이 규칙은 개발 자료에서 검수한 18개 유형을 그대로 입력하는 표 조회와 다르다. 사전 합성 테스트에는 명시 부위, `다른 기기`, 같은 제품명 앞의 `다른`, 지시어·축약어·문맥 의존, B 공란, 잘못된 원문 구간을 넣는다. 구현이 이 문서의 규칙과 다르면 실행 전에 문서와 코드를 함께 바로잡고 고정한다.

## 평가 경계와 집계

- 이미 노출된 ES 20사례·22검수 사건을 사용한다. 발생하지 않은 사건 3개는 관계 판단을 호출하지 않는다. 남은 **19사건**은 관찰된 현재 제품 위험 8, 관찰된 다른 출처 위험 9, 발생 불확실한 현재 제품 위험 1, 관찰됐으나 주체 불명 1이다. 마지막 사건 ES17은 `B=null`이므로 `unknown` 보류를 확인한다.
- 관계 출력 `current / other / unknown`, 각 범주 정답, 확정률(두 확정 관계 수/19), 확정된 사건의 조건부 정답률(분모 0이면 미정의), 미확정 사건의 사유를 보고한다. 정답 관계는 **예측이 끝난 뒤에만** 비교한다.
- 기존 `route_for_events`에 검수된 발생 상태와 예측 관계를 넣어 20사례의 조건부 경로를 계산한다. 관찰된 현재 위험의 즉시 조치 누락을 사건 수와 사례 수로 별도 집계하고, 다른 출처를 현재 제품의 직접 위험으로 오경고한 사례, ES01/09와 ES02/11의 대비쌍, ES06의 두 사건 우선순위, ES17의 확인 경로를 따로 확인한다. 이는 A/E/B 오라클 조건의 **조건부 경로**이며 실제 서비스 경로 점수가 아니다.
- 잘못된 구간이나 예측 예외는 **22사건 중 오류**로 따로 세고, 발생 사건의 관계를 `unknown`으로 보류한다. 미발생 사건의 관계는 기존 계약대로 `null`로 둔다. 오류가 있는 사례는 보통 안전 확인 경로로 보내지만, 같은 사례에 이미 확인된 관찰 현재 위험이 있으면 기존 경로 규칙대로 즉시 안전 조치를 우선한다. 관찰 현재 위험 사건의 관계 누락과 사례의 실제 경로 누락을 각각 집계한다. 개발 안전 관문은 관찰된 현재 8/8, 불확실 현재 1/1, 다른 출처 9/9, 출처 불명 1/1, 조건부 경로 20/20, 대비쌍 2/2, 오류 0/22다. 한 항목이라도 실패하면 서비스 미연결이다. 이 관문은 이슈 #93의 별도 RE/V 개발 회귀 관문과 새 미노출 평가를 대체하지 않는다.

## 실행 순서와 보존

코드·합성 테스트·이 문서와 ES 입력의 파일 해시를 먼저 Git 커밋에 고정한다. 실행용 프로토콜에 코드 커밋, 입력 SHA-256, 사건 순서, 규칙 버전, 집계식, 재시도 없음, 외부 모델 호출 없음과 서비스 미연결 경계를 기록한 뒤 별도 커밋한다. 그 후 ES 개발 자료를 한 번 계산하고 공개 집계·사건별 예측을 보존한다. **설계자가 이미 ES와 정답을 본 상태이므로 이 고정은 재현 조건 고정이며 블라인드 사전등록이 아니다.** 오류가 있으면 원본을 덮어쓰지 않고 원인을 기록하며 새 버전을 만든다. TX·GB 봉인 자료는 열지 않는다. AWS·KT cloud·Docker는 사용하지 않는다.
