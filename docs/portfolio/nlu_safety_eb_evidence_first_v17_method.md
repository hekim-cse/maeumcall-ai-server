# A/S 후보 관계를 원문 근거에서 도출하는 개발 진단

[v16](nlu_safety_label_order_v16_result.md)에서 상태 설명 순서를 뒤집자 네 후보의 응답이 모두 바뀌었다. 상태 정답은 두 조건 모두 1/4였다. 같은 라벨의 설명 순서를 더 탐색하면 그 네 후보에 맞는 순서를 고를 수는 있어도, 후보별로 다른 근거를 찾는지는 확인하기 어렵다.

## 출력 계약

[실험 계약](../../experiments/as_safety_atomic_edges_v17/evidence_contract.py)은 기존 번호 문장, 고정된 사건 E와 후보 B를 사용한다. 모델은 후보가 출처라는 근거, 후보를 출처에서 제외하는 근거, 출처가 불확실하다는 근거를 각각 원문에서 인용하거나 공란을 반환한다. 서버는 인용이 해당 문장에 정확히 한 번 나타나는지 검증하고, 유효한 출력에서 아래와 같이 상태와 근거 문장 번호를 결정한다.

| 출력된 근거 | 결정 |
| --- | --- |
| 출처만 있음 | `supported`, 출처 근거 문장 |
| 배제 근거 있음, 출처 근거 없음 | `unsupported`, 배제 근거 문장 |
| 불확실성만 있음 | `insufficient`, 불확실성 근거 문장 |
| 모두 공란 | `insufficient`, 문장 번호 공란 |
| 출처와 배제 또는 불확실성이 함께 있음 | 계약 오류 `conflicting_source_evidence` |

사건의 출처가 불명확해도 제시된 후보가 현상 자체라는 판단은 가능하다. 이 경우 배제와 불확실성 근거를 모두 보존한다. 원문 인용 검증은 인용의 출처를 확인하는 장치다. 인용이 실제로 관계를 뒷받침하는지는 별도로 대조한다.

## 실모델 검증 계획

1. 기존 검수 PC01·NC01 네 쌍을 사용한다. 정방향 질문과 역방향 질문을 비교하되 응답 스키마, 모델, 컨테이너, 생성 설정을 동일하게 유지한다. 두 조건의 차이는 사용자 메시지 내 질문 세 줄의 순서다. v16 대비 계약과 프롬프트가 모두 달라지므로 v16과의 차이에서 단일 원인 효과를 추정하지 않는다.
2. 실행 전에 코드·입력·모델·이미지의 식별 정보와 요청 해시, 호출 순서를 고정한다. 후보별 두 조건의 원문 인용·상태·근거 문장을 비교하고, 계약 오류와 재시도를 기록한다. 같은 후보의 두 조건이 다른 근거를 제시하면, 상태가 같아도 그 변화를 기록한다.
3. 조건별 상태와 근거 문장 번호가 각각 4/4 일치하고 계약 오류가 0건인지 확인한다. 정확한 문장 안에서도 관계와 무관한 구절을 뽑을 수 있으므로, 통과를 판단하기 전에 실제 인용의 의미를 검토한다. 이 관문을 통과한 후보만 새 미노출 사례에서 검증한다. 이번 묶음은 기노출 개발 자료다.

현재 구현 범위는 요청·응답 계약과 오프라인 테스트다. 테스트의 인용은 사람이 읽을 수 있게 작성한 예시이며 실모델 응답이 아니다. 실행기 연결과 사전 프로토콜 고정 이후에 Q5 검증을 진행한다.
