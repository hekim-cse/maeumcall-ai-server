# A/S 위험 출처 근거 연결 개발 실험 설계

> 2026-11-16 설계 초안. 모델 실행 전 방법을 정리한다. ES01–ES20은 이미 모델에 노출된 AI 작성·사용자 검수 개발 자료다. TX·GB 봉인 자료는 후보 설계·선택·모델 호출에 사용하지 않는다.

## 왜 새 표현이 필요한가

기존 E/B/C 추출도 두 단계였다. 첫 호출에서 사건 E, 물리적 주체 B, 소속 대상 C를 한꺼번에 인용하고, 다음 호출에서 A와의 관계를 물었다. 따라서 단순히 `E→B→A`라고 이름 붙이는 것은 새 방법이 아니다. 이번 후보는 **사건과 주체의 연결** 및 **주체와 접수 제품의 연결**을 각각 명시적인 원문 근거와 유형으로 출력하고, 두 단계의 오류를 따로 측정한다. 원문 구절이 존재한다는 기계적 검증은 그 연결의 의미가 옳다는 보증이 아니다.

직전 ES 사건 오라클 조건에서 관계는 7/19였고, 관계만 출력한 R은 19건 모두 `other`로 답해 현재 제품의 관찰 위험 8/8을 놓쳤다. 검수 주체를 제공한 O도 관계 5/18, 인용 계약 오류 5/18이었다. 앞선 대칭 질문도 RE/V 22건에서 관계 6/22, 현재 제품의 관찰 위험 3/13으로 실패했다. 원문 후보 ID 추출 비교는 다른 RE/V 6건에서 정답 E/B/C 구절 후보 포함 13/18, 모델 선택 정확 일치 0/18이었다. **이 13/18은 ES 주체 후보 15/18과 자료·분모가 다르다.**

## 개발 후보

1. 원문만 보고 절·시작/끝 위치·원문 그대로의 인용으로 후보 구절을 만든다. 이 **별도 후보 가용성 감사**에는 검수 정답을 생성 입력으로 사용하지 않고, 생성 후에만 대조한다. 현재 근거 연결 모델 요청에는 후보 목록을 전달하지 않는다. 후보 수 제한에 잘린 경우와 생성 단계에서 빠진 경우를 구분한다. ES에서 기존 후보 생성기의 비공란 주체 포함은 15/18이다. ES05 `등받이 뒤`, ES13 `전동 드릴 배터리`, ES15 `전자담배 충전기`는 후보 제한이 아니라 생성 자체에서 누락됐다.
2. 개발 진단 모델에는 검수된 접수 제품 A와 검수된 사건 E·발생 상태만 입력한다. B·관계·경로 정답은 전달하지 않는다. 이는 사건 인식 성능을 측정하지 않는 **사건 오라클 조건**이다. 모델은 각 E에 연결되는 물리적 발생 주체 B의 원문 구절과 연결 근거를 별도 필드로 낸다. 사건이 없는 곳에서 B를 강제하지 않는다.
3. 모델은 B와 A 사이를 `same_entity`, `part_of`, `coreference`, `distinct`, `unresolved` 중 하나와 그 판단에 사용한 원문 구절로 표현한다. 출력 계약은 근거 구절의 위치·존재·최소 구간 연결, 필드 일관성, 허용 유형만 검증한다. `current`는 앞의 세 유형, `other`는 `distinct`, 나머지는 `unknown`으로 투영하되, 원문 근거의 **의미 타당성**은 사람 확정 정답과 대조해 별도 점수로 기록한다. 계약 오류나 불확실 관계는 안전 확인 경로로 둔다. 모델의 `distinct` 주장과 원문 인용만으로 물건이 실제 별개임을 증명했다고 취급하지 않는다. 따라서 이 경로 계산은 개발용 예측이며 서비스 안전 분기에 연결하지 않는다.
4. 노출된 ES 개발 자료에서는 후보 구절 재현율, E→B 연결, B→A 관계, 최종 안전 경로를 분리해 측정한다. 주체가 공란인 ES17과 미발생 사건은 각 단계의 적격 분모에서 별도 제외하며, 전체 사례 경로와 모델 관여 사례 경로를 구분한다. ES06·15의 복수 사건은 사건 단위와 사례 단위를 혼합하지 않는다.

## 반증 기준과 경계

최소한 관찰된 현재 제품 위험 8건의 관계를 모두 `current`로, 관찰된 다른 출처 위험 9건의 관계를 모두 `other`로, 출처 불명 1건과 발생 불확실한 현재 제품 1건을 각각 `unknown`·`current`로 판정해야 한다. 사건별 관계와 사례별 최종 경로는 구분한다. 특히 ES06은 다른 출처 사건과 현재 제품 사건이 함께 있으므로, `other` 사건이 있어도 현재 제품의 관찰 위험이 있으면 사례 경로는 안전 우선이다. 사례 경로의 우선순위는 `safety_action_required` > `confirming_safety_status` > `collecting_service_request`로 고정한다. 모델 관여 18사례의 경로 18/18, ES01/09와 ES02/11의 관계·사례 경로가 양쪽 모두 맞는 대비쌍 2/2, 계약·전송 오류 0건도 요구한다. 범주별 분모와 실제 적격 사건 수가 구현 조건에 따라 달라지면 실행 전에 프로토콜에 다시 고정한다. 어느 문턱이든 실패하면 서비스 안전 분기에 연결하지 않는다. 이 작은 개발 문턱을 통과해도 배포 안전성을 뜻하지 않는다.

실험 코드·입력·모델 파일·요청 조건·계산식·독립 검증기를 모델 호출 전에 커밋 및 해시로 고정한다. 원시 응답은 저장소 밖 소유자 전용 위치에, 공개 저널은 원문·프롬프트·원시 본문 없이 저장한다. 결과의 차이는 같은 노출 사례에 대한 조건부 진단으로만 해석한다. 새 후보를 고른 뒤에는 **모델 미노출 새 발화와 전체 필드 정답을 사용자에게 먼저 검수받고** 입력과 코드를 고정한 다음 한 번 실행한다. AI 작성 발화라면 출처를 명시하고 탐색 평가로 보고하며 공식 전체 정확도나 일반화 개선율로 표현하지 않는다.

## 원문 후보의 사전 점검

새 개발 전용 후보 생성기는 기존 동결 코드를 바꾸지 않고, 한 글자 명사 뒤의 조사와 `에서는`처럼 결합된 조사를 원문 부분 문자열 후보로 추가했다. `python -m scripts.audit_as_safety_source_lattice`로 이미 노출된 ES의 검수 주체 구절 18개를 사후 대조하면 **18/18이 선택 후보에 있고, 잘린 구절과 생성 누락은 각각 0건**이다. ES 사례별 선택 후보 수는 44–122개다. 기존 방식의 동일한 18개에 대한 15/18과 비교할 수 있는 수치는 **후보 목록 포함률**뿐이다. 모델이 그 후보를 고르거나 관계를 옳게 판단한다는 결과는 아직 없다. 이번 점검은 생성기 수정에 사용한 개발 사례이므로 독립 성능 평가가 아니다.
