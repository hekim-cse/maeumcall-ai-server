# A/S 위험 주체 출력 형식 제약 분리 진단 결과

> 2026-11-20. 이미 노출된 AI 작성·사용자 검수 ES 사례 5건의 개발 진단이다. 공식 정확도, 정확도 개선율, 새 사례 일반화 성능 또는 서비스 안전 경로 결과로 사용하지 않는다.

## 고정 조건과 검증

- [사전 설계](nlu_safety_atomic_edge_format_v3_method.md)에 따라 ES01·03·09·17·18의 첫 사건을 각 조건에서 한 번씩, 고정 순서로 총 10회 호출했다. 조건 A는 기존 `json_object`와 세 필드 스키마, 조건 B는 스키마 없는 `json_object`다. 프롬프트·모델·요청 설정·실행 환경은 같고 요청 본문의 유일한 차이는 `response_format`이다. 재시도는 없었다.
- 코드·방법은 커밋 `0464d6b3b40635ed72956309b93f09740df6d038`에서 고정했다. [프로토콜](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-format-v3-development-protocol.json)은 실행 전 커밋 `ed9af80`에 기록했고 SHA-256은 `847dfc8514f39b1d6bcc735c2af651f7123f5a0bba4cbea759687332d8d241be`다. 10개 요청 본문 해시와 호출 순서를 실행 전에 고정했다. A의 다섯 요청 해시는 [이전 비교](nlu_safety_atomic_edge_abstention_v2_development_result.md)의 A와 각각 일치한다.
- 모델 파일 SHA-256은 `644b04cde835d486df33c6d4d7552ba367fcb28802fe39b6b4bb9c60b9ab6f3d`, 이미지 digest는 `sha256:17155a3ce4cc906728ec99a2814bf0b4eaffaf3b4872bad8c3affed310cdbc35`다. 로컬 컨테이너에 CPU 2개·메모리 4 GiB와 127.0.0.1 전용 포트를 지정했다. 실행 뒤 컨테이너와 Docker Desktop을 종료했다. AWS·KT cloud는 사용하지 않았다.
- [공개 저널](../../evals/structured_nlu/data/ai_heldout/as-safety-eb-format-v3-development-journal.v1.jsonl)은 헤더 1개와 결과 10개이며 SHA-256은 `a649b6662135232635057199a949375e5636d6630f3ce492afafcb129c73f366`이다. 원문·프롬프트·응답은 저장하지 않았다. 원시 응답 10개는 저장소 밖 접근 제한 폴더에 보관했다.
- 독립 검증기는 프로토콜·요청·저널·원시 응답의 해시와 순서, 출력 계약, 검수 정답을 다시 확인했다. 검증기 파일 SHA-256은 `aa879eb672ce5203fefa600d6cc2c409920b723c64079241106a8566c496d371`이다. A의 원시 응답은 이전 비교의 같은 다섯 응답과 모두 바이트 단위로 일치했다. 검증기는 실행 후 현재 파일의 내용이 고정 커밋과 같은지 검사하는 대상에서 자기 자신을 제외하므로, 재검증 시 이 SHA-256도 함께 대조해야 한다.

## 조건별 관찰

| 지표 | 스키마 지정 A | 스키마 제거 B |
| --- | ---: | ---: |
| 모델 호출 | 5/5 | 5/5 |
| 전송·종료 오류 | 0/5 | 0/5 |
| 출력 계약 통과 | 5/5 | 0/5 |
| 출력 계약 오류 | 0/5 | 5/5 |
| 유효한 `unresolved`·두 공란 | 5/5 | 0/5 |
| 유효 출력에서 비공란 B 원문 구절 일치 | 0/4 | 평가 불가 |
| 유효 출력에서 E→B 종류 일치 | 1/5 | 평가 불가 |
| 유효 출력에서 E→B 근거 일치, 공란 포함 | 1/5 | 평가 불가 |
| 유효 출력에서 비공란 근거 일치 | 0/4 | 평가 불가 |
| ES17의 유효한 정당한 공란 | 1/1 | 평가 불가 |

B의 다섯 응답은 모두 HTTP 전송과 JSON 파싱을 통과했고 세 키도 포함했다. 그러나 `subject_span`과 `event_subject_evidence_span`을 계약에서 요구한 공란 또는 `{clause_index, quote}` 객체 대신 문자열로 반환했다. 독립 검증기의 실패 분류는 5건 모두 `quote fields invalid`였다. `event_subject_kind`는 다섯 건 모두 허용된 `location` 값이었다. 따라서 B의 오류는 고정 이미지가 일반 `json_object` 요청을 거부한 전송 오류가 아니라 **인용 필드 형태의 계약 오류**다. 문자열을 사후에 구절 객체로 변환하거나 정답으로 채점하지 않았다.

이 다섯 사례에서는 스키마 제약을 제거하자 JSON과 키는 유지됐지만 유효한 구조화 출력을 얻지 못했다. A는 이전 전건 보류를 그대로 재현했다. **이 결과만으로 스키마가 전건 보류의 원인이라고 확정할 수 없고, B의 주체 추출 정확도나 ES17의 안전한 보류를 비교할 수 없다.** 특히 B의 ES17을 `오확정 0건`으로 표현하면 무효 출력을 안전한 판단으로 오해할 수 있어 점수로 사용하지 않는다.

기존 19건 개발 관문은 여전히 미달이며 이번 5건은 그 관문을 대체하지 않는다. B→A 관계와 최종 안전 경로는 평가하지 않았고 서비스에도 연결하지 않았다. 다음에는 형식 계약을 유지한 채 주체·근거의 동시 요구를 별도 변수로 분리할 수 있다. 후보를 선택한 후에는 새 미노출 검수 사례에서 다시 평가해야 한다. TX·GB 봉인 자료는 사용하지 않았다.
