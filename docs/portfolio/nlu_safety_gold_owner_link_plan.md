# A/S 위험 출처 연결만 분리하는 진단 계획

## 반증할 가설

앞선 [출처 근거 진단](nlu_safety_owner_evidence_diagnostic_result.md)에서는 다른 출처 6건이 모두 `current` 오답이었다. RE10·RE11·V02는 위험 주체의 검수 구간을 정확히 인용하고도 접수 대상에 속한다고 잘못 연결했다. 다만 해당 후보가 출처 구간 추출과 관계 판단을 한 번에 출력했으므로 어느 부분이 오류를 유발했는지 더 분리할 필요가 있다.

이번에는 검수된 **위험 주체 구간과 문장 번호를 정답 입력으로 추가**하고, 기존 단일 관계 오라클의 나머지 원문·접수 대상·위험 사건·발생 상태 입력 및 출력 형식을 최대한 유지한다. 모델에는 `source_relation` 하나만 묻는다. 다른 출처 6건이 여전히 `current`라면 Q5의 개체 연결 판단 또는 출력 편향 문제를 더 의심할 수 있다. 회복되면 앞 단계의 주체 추출·여러 출력 필드 결합 문제를 조사할 근거가 생긴다. 어느 경우에도 원인을 단정하지 않는다.

## 사례와 누출 경계

사용자가 이미 검수한 [주체 정답](../../evals/structured_nlu/data/ai_heldout/as-safety-owner-evidence-reviewed.v1.json)에서 비공란 구간이 있는 22건만 사용한다. 정답 관계는 `current` 16건, `other` 6건이며 RE07·V09의 `unknown` 2건은 제외한다. 두 사례에 `null` 주체를 제공하면 정답 `unknown`을 누출하기 때문이다. 모델의 `unknown` 출력은 보류로 허용하고 별도 집계한다. **정답 연결 종류나 관계값은 모델 입력에 포함하지 않는다.**

RE06의 `커피머신 물통`은 실제 누출일 경우의 조건부 주체이며 발생 상태 `uncertain`은 그대로 유지한다. V03의 접수 대상은 전기포트, V04는 이번 진단에서만 토스터다. 기존 V04 정답·과거 점수는 바꾸지 않는다. V03·V04 제외 20건과 RE06 제외 21건도 별도 민감도로 보고한다.

## 실행과 판단

같은 로컬 Kanana Q5 모델·컨테이너·요청 정책으로 ID 순서의 22건을 각 한 번 호출한다. 호출 전 코드·검수 입력·모델·정책·독립 검증기 해시와 Git 커밋을 고정한다. 저널에는 시작·종료·유한 판단·오류 단계/유형/코드·지연만 기록하고 발화, 검수 구간, 모델 응답 본문은 기록하지 않는다. 중단 시 자동 재시도하지 않는다. 독립 검증기는 45행의 순서·중복 JSON 키·해시·분모·관계·경로·대비쌍을 재검산한다.

사전 개발 기준은 `current` 최소 15/16, `other` 6/6, 호출·계약 오류 0/22와 V01/02·V05/06·V07/08 대비쌍 반전 3/3이다. `unknown` 출력 수, RE06과 V03·V04 제외 민감도, 단일 실행 지연도 함께 보고한다. 기준을 통과해도 접수 대상·위험 사건·위험 주체의 정답 구간을 실제 서비스에서 얻는 방법은 아직 검증되지 않는다. 이 기노출 AI 작성 개발 집합으로 공식 전체 정확도, 개선율 또는 실서비스 안전 성능을 주장하지 않는다.
