# 내부 test64 짝 비교 도구 (준비 단계)

이 디렉터리는 **새 AI 작성·사용자 검수 사례 64건**의 후보 코드 고정 후 평가를 위한 도구다. 사람 직접 작성 발화의 모집단 정확도나 외부 벤치마크를 뜻하지 않는다. 입력 데이터와 프로토콜이 아직 커밋되지 않았으므로 현재 실모델 실행은 준비되지 않았다.

## 사전 등록 조건

- 기준 코드 `c46c27a52bc8cfc6e11bfa62985aa6a90d6f4da3`, 후보 코드 `04af27849563f7b30845441e0f8fc6ca90f876ff`; 새 TEST 데이터는 두 코드가 공유하는 별도 `input_commit`에 커밋한다. 기준 코드 트리에는 새 TEST 파일이 없어도 된다.
- 검수된 test dataset, review ledger, case decisions와 validation dataset, known corpus inventory를 입력으로 묶는다. 16개 업무마다 인사/후속 상태 × 업무 안/밖 1건씩 총 64건이어야 한다. 모든 사례는 `adjudicated`여야 한다.
- `NFC+strip` 텍스트 해시로 기존 저장소 데이터 corpus와 validation의 **정확히 같은 발화**를 거른다. 문서, 과거 실행 원문, 의미가 비슷한 발화, 모델의 다른 노출은 여기서 완전히 검사하지 못한다. 평가 전에 이전 문서·실행 원문을 포함하는 노출 목록과 의미 유사성에 대한 사람 검토가 별도로 필요하다.
- 16개 업무와 2개 범위로 만든 32개 층마다 2건을 짝지으며 인사 사례는 기준→후보, 후속 사례는 후보→기준 순서로 실행한다. 같은 Q5 파일, 컨테이너 이미지, 10 GiB 실행 한도, 요청 설정을 사용한다.
- 원문 응답은 작업 트리 바깥 0700 디렉터리에 0600으로 기록한다. 8 arm 평가마다 수동 Docker 재시작하며 같은 컨테이너 ID, 새 `StartedAt`, 그대로인 자동 `RestartCount`를 확인한다. 통신 오류, OOM, 소스/입력 변경, 예상 밖 재시작은 결과 확정을 중지한다.
- 결과 JSON은 처음에 `unverified`다. 별도 `verify.py`가 원문 해시·저널·각 arm의 원문 재생을 확인하고 수치와 기술적 verified receipt를 생성한다. 재생은 같은 분석 함수·채점 함수를 다시 사용하므로 **독립 구현의 점수 검증은 아니다**. 95% 구간은 32개 업무×범위 층에서 각각 2건을 복원추출하는 짝 부트스트랩 20,000회, seed 0, 정렬 표본의 위치 `p×(n−1)` 선형 보간으로 계산한다. 이 구간은 내부 사례의 기술통계다.

## 별도 안전 관문과 발표 경계

test64의 A/S 4건만으로 안전 경로를 평가할 수 없다. [사전 표본 설계](../../docs/portfolio/nlu_internal_test64_sampling_plan_v1.md)에 따라 신규 SS01–SS16을 별도 검수·동결한다. 이 도구의 `safety16` 프로토콜은 현재 제품 실제 위험·불확실·다른 출처·가정/부정 각 4건과 개별 범주 ledger를 요구하고, 같은 두 코드와 Q5 조건에서 32 arm을 짝 실행한다. 사전 검사에서 직접 위험은 `safety_issue`, 불확실·다른 출처는 안전 필드 공란, 가정·부정은 공란 또는 `no_safety_issue` 정답만 허용한다. 원문 재생 검증 뒤 `safety_status=safety_issue`에 따른 즉시 보호 경로를 범주별 건수로 보고한다. 직접 위험의 후보 누락과 기준선에서 새로 생긴 누락, 다른 출처·미발생의 오경고를 각각 분모와 함께 기록한다. 직접 위험 4건에서 새 누락이 하나라도 있으면 개선 확인 문구를 사용하지 않는다. SS16은 test64 정확도 분모에 합치지 않는다. 검수 범주 ledger 자체의 사람 판정은 실행 전에 별도로 확인해야 한다.

test64 receipt는 `publication_status=provisional_pending_fresh_safety16_and_exposure_audit`와 `safety_condition=unverified`를 유지한다. safety16 receipt는 별도로 발급되며 test64 receipt를 자동으로 확정하지 않는다. SS16 검증과 과거 문서·원문을 포함한 노출 감사가 끝나기 전에는 정확도 개선을 확정했다고 쓰지 않는다.

## 현재 한계

- 실제 test64·SS16 자료의 전체 검수, 문서·과거 원문을 포함한 노출 및 의미 유사성 감사, 모델 파일 검증, Docker 실행, 원문 재생 완료 기록이 없다. 이 디렉터리의 코드는 실험 결과나 정확도 개선율의 증거가 아니다.
- 합성 fixture로 두 Git 작업 트리의 입력·프로토콜 커밋, 64+16건의 가짜 Q5 짝 실행, 원문 재생, 검증 receipt와 원문 변조 거절을 테스트했다. 이는 실제 모델 성능이나 사람 검수의 대체가 아니다.
- 테스트는 저장소의 `.venv`에서 실행한다.
