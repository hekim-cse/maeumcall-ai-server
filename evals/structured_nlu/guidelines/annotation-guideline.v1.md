# 구조화 NLU 정답 작성·검수 지침 V1

이 문서는 마음콜의 구조화 NLU 상세 그래프 16개에 사용할 골든 데이터의 정답을
같은 기준으로 작성하고 검수하기 위한 기준이다. 실제 사용자 대화나 개인정보를
복사하지 않고 프로젝트 요구사항에 맞춰 직접 작성한 발화만 사용한다.

## 한 case가 나타내는 것

한 case는 모델 호출 한 번이다. 현재 시나리오, 대화 상태, 이전 턴까지 모은 값,
서버가 제시한 예약 대안 시간, 사용자의 이번 발화와 이번 발화에서 추출해야 할
정답만 포함한다. 여러 턴의 대화를 한 case에 합치지 않는다.

## 정답 필드 판정

- 사용자가 이번 발화에서 직접 말했거나 문장 안에서 명확하게 지시한 값만
  `labels.fields`에 기록한다.
- 말하지 않은 필드는 키를 없애지 않고 `null`로 둔다. 키 누락과 `null`은 다르다.
- `accepted_values`에는 모델 출력으로 정확히 인정할 정규화 결과만 넣는다.
  표현을 많이 넣어 점수를 쉽게 만드는 용도로 사용하지 않는다.
- 선택형 필드는 서비스 계약에 등록된 canonical value 하나만 허용한다.
- 이전 턴의 값은 `current_fields`에만 기록한다. 사용자가 이번에 다시 말하지 않은
  값을 현재 발화의 새 추출값처럼 복사하지 않는다.

## 행동과 필드의 관계

- `user_action`은 현재 `conversation_state`에서 실제로 허용된 행동만 선택한다.
- 정보 제공 행동은 이번 발화에서 최소 하나의 새 필드를 제공해야 한다.
- 확인·완료·취소·종료처럼 새 값을 받지 않는 행동에는 새 업무 필드를 넣지 않는다.
- 변경 행동은 계약이 허용한 대상 필드만 포함한다. 값을 함께 말했으면 해당 값을
  기록하고, 변경 의사만 말했다면 대상 필드는 `null`로 두어 다시 수집하게 한다.
- 배달·시청·고객센터 workflow의 `change_detail`은 `change_field`로 변경 대상을
  명시하고 다른 필드는 새 값으로 만들지 않는다.

## 예약 대안 시간

- `offered_alternative_times`는 모델이 만든 값이 아니라 서버가 해당 턴에 실제로
  제시한 후보 목록이다.
- 대안 선택 상태가 아니면 목록은 비워 둔다.
- `select_alternative_time`과 `selected_time`은 함께 존재해야 한다.
- `selected_time`은 후보 문자열 중 하나와 정확히 일치해야 한다. 공백이나 표현을
  임의로 보정하지 않는다.

## 태그 판정

- `single_field`와 `multi_field`는 정답 필드 개수에서 계산되는 객관 태그다.
- 확인·취소·종료·안전 태그는 실제 행동 및 상태 계약과 일치해야 한다.
- `ambiguous`, `colloquial`, `hard_negative`, `ellipsis`, `negation`은 문장만 보고
  판단하지 말고 현재 상태와 기대 행동을 함께 확인한다.
- 애매한 문장을 억지로 한 행동에 맞추지 않는다. 서비스가 `unknown`을 허용하는
  상태라면 모호함 자체를 정답으로 남길 수 있다.

## 의미 그룹과 split

- 같은 의미 원본에서 만든 패러프레이즈와 대조 사례는 같은
  `conversation_group_id`에 둔다.
- 동일 그룹의 split은 그룹 파일이 아니라 별도 split 배정 원장에서 한 번만 정한다.
- 의미 그룹과 초안 case 목록을 만든 뒤, 모델 결과를 보기 전에 split을 확정한다.
- 모델 결과를 본 뒤 유리한 문장을 validation이나 test로 옮기지 않는다. 변경이
  필요하면 새 데이터 버전과 PR에서 이유를 남긴다.

## 검수 상태와 adjudication

- `draft`: 최초 작성 상태다. 정식 점수 계산에 사용할 수 없다.
- `reviewed`: 필드와 행동을 다시 확인했지만 의견 충돌이나 미확정 사항이 남을 수
  있다. 정식 점수 계산에 사용할 수 없다.
- `adjudicated`: 이 지침과 라이브 서비스 계약을 기준으로 최종 정답을 확정한
  상태다. validation과 test의 공식 후보 데이터는 이 상태여야 한다.
- 검수 원장에는 case ID, 최종 case 내용의 SHA-256, 가명 adjudicator ID, 확정 시각,
  판단 근거를 기록한다.
- case 내용이 바뀌면 SHA-256도 달라지므로 기존 승인을 재사용하지 않고 다시
  검수한다.

## 개인정보와 작성 금지 항목

- 실제 사용자 이름, 전화번호, 주소, 주문번호, 학번, 진료정보를 복사하지 않는다.
- 예시는 명백한 가상 값으로 작성하고 실제 계정이나 운영 기록과 연결하지 않는다.
- 모델이 잘 맞히도록 특정 후보 모델의 답변 표현을 그대로 정답 문장에 복사하지
  않는다.
- validation과 test 결과를 확인한 뒤 정답이나 split을 조정하지 않는다.

## 검수 예시

사용자 발화가 “내일 오후 세 시로 바꿔 주세요”이고 현재 상태가 예약 확인이라면,
변경 행동과 날짜·시간의 새 값이 함께 들어갈 수 있다. 반대로 “날짜를 바꿀게요”라면
변경 대상은 날짜지만 새 날짜 값은 `null`이어야 한다.

사용자 발화가 “네, 그렇게 해 주세요”인 확인 단계라면 확인 행동만 정답이다.
이전 턴의 날짜와 시간을 이번 발화에서 새로 추출한 것처럼 넣지 않는다.
