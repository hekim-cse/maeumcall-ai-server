# 탐색적 실모델 관측 (2026-10-09)

`exploratory-local-2026-10-09.json`은 로컬 ARM Docker 이미지
`sha256:448fdff14781d4dd40a5b664dcfdd909e6a93a557f7803d110381394b736f271`에서
개발용 초안 36건 중 16개 상세 시나리오별 정보 제공 사례 한 건씩 `/chat`에 보낸 기록이다.
프롬프트와 답변 전문은 저장하지 않았고, corpus SHA와 사례 ID로 입력을 추적한다.
이미지의 provider 파일 SHA는 기록했지만 전체 이미지 소스 트리와 특정 Git 커밋의
동일성은 검증하지 못했다. 실행 당시 probe 스크립트도 미커밋 상태였다.

- HTTP 200: 13/16. 나머지 3건은 `AI_RESPONSE_VALIDATION_FAILED`로 HTTP 502.
- 성공 요청의 지연시간 중앙값: 57.855초. 이는 실패 요청을 제외한 값이다.
- 실패: 배달 환불/재배달(164.577초), 시청 주민등록 등본(119.348초), 병원 예약(71.839초).
- 병원 예약의 별도 진단에서 모델이 필수 `selected_time` 키를 생략했다. 이 경우
  서버의 엄격한 출력 계약이 잘못된 상태 반영을 막았으나, 사용자는 오류를 받았다.
- 환불·재배달의 별도 진단에서는 모델이 필수 `change_field` 키를 생략했다.
- 주민등록 등본의 별도 진단에서는 `provide_details`를 선택하면서 이번 턴의
  필드 네 개를 모두 `null`로 반환했다. 현재 계약에 이 출력은 모순이다.

세 실패의 원인은 모델 원문을 보관한 공식 평가 결과가 아니라 별도 재현 실행에서
관찰한 출력이다. 현재 검증기에 해당 출력을 다시 넣어도 같은 계약 오류가 난다.
실행 간 모델 출력이 달라질 수 있으므로 16건 원 실행의 정확한 원인이라고 단정하지 않는다.

이 기록은 정확도 평가나 32개 전체 흐름의 품질 점수가 아니다. 정답이 확정된
validation/test 케이스와 반복 실행이 아직 없다. ARM 로컬과 아래 x86 EC2 결과도
하드웨어가 달라 직접적인 전후 성능 비교로 사용할 수 없다.

## x86 비공개 EC2에서 수행한 성능 실험

동일한 x86 probe 이미지와 같은 합성 병원 예약 입력(765 입력 토큰, 56 출력 토큰),
`m7i-flex.large`, PyTorch 1 CPU 스레드에서 콜드 부팅 첫 요청을 비교했다.
애플리케이션 준비 시간과 `/chat` 응답 시간은 별도 계측했다.

| 시작 방식 | 준비 시간 | 첫 `/chat` | 준비+첫 `/chat` |
| --- | ---: | ---: | ---: |
| 워밍업 없음, 1회 | 1.52초 | 60.542초 | 약 62.06초 |
| 1토큰 워밍업, 2회 | 32.24초 | 39.843초 / 41.271초 | 약 72.08초 / 73.51초 |

워밍업은 사용자가 요청을 보낸 뒤 기다리는 시간을 줄였지만 계산을 시작 단계로
이동시켰다. 관측한 총 소요 시간은 오히려 길었으며 표본도 적어 총 성능 개선으로
주장할 수 없다. 따라서 `HF_WARMUP_ON_STARTUP` 기본값은 `false`다.

같은 인스턴스의 별도 2 CPU 스레드 probe에서는 첫 요청 65.238초,
후속 요청 46.014초였다. 1 CPU 스레드 후속 요청 41.331초와 40.523초보다
빠르지 않았다. 실행 순서와 캐시 효과가 통제되지 않았으므로 스레드 수 변경을
최적화 결과로 채택하지 않았다. `HF_CPU_THREADS`는 후속 통제 실험용 선택 설정이다.

다음 성능 개선 후보는 양자화된 런타임의 동일 입력 반복 측정이다. 품질 검증 전에
속도만으로 런타임을 교체하지 않는다.

## 로컬 Q5 GGUF 탐색 (2026-10-09)

AWS 인스턴스를 시작하지 않고 로컬 Docker Desktop의 ARM CPU에서 병원 예약
development 초안 `reservation-hospital-human-information-provision-001.c1` 한 건을
각 실행 방식으로 세 번 생성했다. 두 컨테이너 모두 2 CPU로 제한하고 내부 스레드도
2개로 설정했다. 이 한 건은 공식 validation/test 케이스가 아니다.

- Q5 GGUF: 제3자가 변환한 [모델 저장소](https://huggingface.co/TaeyoungLeeJack/kanana-1.5-2.1b-instruct-2505-Q5_K_M-GGUF)의
  개정 `f2f883a35e6183c00fcb70e22a010ce7745ea0b4`, 파일 SHA-256
  `644b04cde835d486df33c6d4d7552ba367fcb28802fe39b6b4bb9c60b9ab6f3d`.
  공식 `llama.cpp` 서버 이미지 digest와 생성 설정은 결과 JSON에 기록했다.
- GGUF에서 종료 토큰 `<|eot_id|>`을 stop 조건으로 지정하지 않은 첫 탐색은
  JSON 뒤에 그 토큰이 붙어 **3/3 JSON 파싱 실패**였다. stop 조건으로 다시 실행한
  [기록](exploratory-q5-hospital-2026-10-09.json)은 구조적 계약 **3/3 통과**.
  첫 요청 15.500초, 프롬프트 캐시가 적용된 후속 요청 3.082초와 3.071초였다.
  그러나 세 번 모두 사용자 발화의 `3시`를 `오후 3시`로 바꿔 초안의 허용값과
  **시간 필드가 불일치**했다. 이 값은 사용자가 말하지 않은 시간대를 추가한다.
- 동일 호스트의 기존 HF 모델 [기록](exploratory-hf-hospital-2026-10-09.json)은
  136.489초, 138.591초, 138.454초였고 세 번 모두 필수 출력 키 누락으로
  구조적 계약을 통과하지 못했다. 기준 실행기는 당시 임시 스크립트였으며
  생성 토큰 수를 결과에 저장하지 않았다. 모델 로드 4.236초는 요청 시간에서
  제외했다.

GGUF는 64개 출력 토큰을 생성했고, 후속 두 요청에서는 771개 입력 토큰이
프롬프트 캐시에서 재사용됐다. 기존 HF 실행의 출력 토큰 수는 기록되지 않아
이 결과로 동일 작업당 속도 향상률을 계산할 수 없다. 양자화 모델은 이 사례에서
사실 추가가 관찰됐으므로 서비스에 연결하지 않았다. 입력·출력 전문은 결과 JSON에
넣지 않았다. `scripts/probe_gguf_hospital.py`는 GGUF 결과를 다시 측정하는
스크립트이고, 기존 HF 기준 결과는 임시 실행기로 수집했다.

## 동일 Q5 모델의 16개 상세 시나리오 탐색

같은 Q5 파일과 `llama.cpp` 이미지에서 2 CPU·2 스레드·컨텍스트 4096으로 서버를
로컬에 다시 띄웠다. `scripts/probe_gguf_structured_nlu.py`가 16개 시나리오의
사람 작성 development **초안**에서 정보 제공 사례를 한 건씩 선택해 해당 라이브
분석기와 검증기를 실행했다. 검증 실패 시 서버 코드와 동일하게 최대 두 번 생성했다.
원문 없이 사례 ID, 요청 시간, 토큰 수, 계약 통과 여부, 초안과 다른 필드 이름만
[결과 파일](exploratory-q5-16-development-2026-10-09.json)에 남겼다.

- 출력 계약 통과: 15/16. 주민등록 등본 문의는 두 번 모두 실패했다.
- 계약 통과와 별도로 **초안의 모든 라벨과 정확히 일치**: 3/16.
  나머지 12개 계약 통과 사례는 하나 이상 불일치했다. 이는 검수되지 않은 초안과
  정확한 허용 문자열 목록의 대조이지 공식 정확도가 아니다.
- 요청 시간 중앙값 20.800초, 최소 10.681초, 최대 27.573초.
  16개 요청 시간 합은 312.371초이며 총 17번 생성했다. 캐시·출력 토큰 수는
  사례마다 달라 이 숫자를 앞선 HF `/chat` 탐색과 배속으로 비교할 수 없다.
- 병원 예약의 `time` 불일치처럼, 구조적 계약 통과만으로 사용자가 말하지 않은
  사실의 추가를 막지는 못했다.

따라서 양자화 실행은 아직 **배포 후보일 뿐 채택되지 않았다**. 다음 비교에는
정답 합의를 마친 validation/test 사례, 같은 실행 경로의 기존 HF 기준 측정,
반복 실행, 캐시·생성 토큰 조건의 통제가 필요하다.

### 초안 불일치 재진단

독립된 검증·구조·문서 검토에서 기존 결과 파일에는 불일치 필드 이름만 있어 원인을
확정할 수 없다고 지적했다. 같은 로컬 Q5 설정으로 불일치 12건과 계약 실패 1건을
한 번씩 추가 실행해 출력을 일시적으로 확인했고, 원문 대신 필드별 분류 코드만
[감사 기록](exploratory-q5-mismatch-audit-2026-10-09.json)에 남겼다. 이 분류는
`ai_assisted_unreviewed`이며 사람의 정답 합의가 아니다.

초안과 불일치한 필드 21개 중 9개는 초안에 값이 있지만 모델이 `null`을 반환했다.
6개는 같은 의미일 가능성이 있는 표현 차이, 1개는 숫자와 단위의 형식 차이
후보이며, 어느 것도 자동으로 정답에 추가하지 않는다. 3개는 발화에 없는
`오후`를 시간에 붙였고, 1개는 `5시`를 `15:00`으로 잘못 바꿨다. 나머지 1개는
환불 가능 여부를 묻는 발화를 희망 처리 `refund`로 읽었지만 초안은 `null`로 둔
사례로, 의미 판단과 초안 검토가 함께 필요하다. 주민등록 등본의 계약 실패는 두
시도 모두 `provide_details`를 선택하면서 이번 턴 필드를 전부 `null`로 둔
행동·필드 모순이었다.

이 재실행은 첫 16건 실행의 출력 원문을 복원한 것이 아니다. 동일 설정에서 관찰한
추가 표본이며, 개별 오류의 반복률이나 모델 정확도를 주장할 수 없다. 다음 단계는
표현·형식 후보와 환불 의사 해석을 사람이 검토하고, 명백한 시간 오류와 누락을
분리해 수정안을 실험한 뒤 검수된 데이터로 재평가하는 것이다.
