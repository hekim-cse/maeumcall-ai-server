# 탐색적 실모델 관측 (2026-10-09)

`exploratory-local-2026-10-09.json`은 로컬 ARM Docker 이미지
`sha256:448fdff14781d4dd40a5b664dcfdd909e6a93a557f7803d110381394b736f271`에서
개발용 초안 36건 중 16개 상세 시나리오별 정보 제공 사례 한 건씩 `/chat`에 보낸 기록이다.
프롬프트와 답변 전문은 저장하지 않았고, corpus SHA와 사례 ID로 입력을 추적한다.
이미지의 provider 파일 SHA는 기록했지만 전체 이미지 소스 트리와 특정 Git 커밋의
동일성은 검증하지 못했다. 실행 당시 probe 스크립트도 미커밋 상태였다.

- HTTP 200: 13/16. 나머지 3건은 `AI_RESPONSE_VALIDATION_FAILED`로 HTTP 502.
- 성공 요청의 지연시간 중앙값: 57.855초. 이는 실패 요청을 제외한 값이다.
- 실패: 배달 환불/재배달(164.577초), 시청 주민등록 등본(119.348초), 병원 예약(71.839초).
- 병원 예약의 별도 진단에서 모델이 필수 `selected_time` 키를 생략했다. 이 경우
  서버의 엄격한 출력 계약이 잘못된 상태 반영을 막았으나, 사용자는 오류를 받았다.
- 환불·재배달의 별도 진단에서는 모델이 필수 `change_field` 키를 생략했다.
- 주민등록 등본의 별도 진단에서는 `provide_details`를 선택하면서 이번 턴의
  필드 네 개를 모두 `null`로 반환했다. 현재 계약에 이 출력은 모순이다.

세 실패의 원인은 모델 원문을 보관한 공식 평가 결과가 아니라 별도 재현 실행에서
관찰한 출력이다. 현재 검증기에 해당 출력을 다시 넣어도 같은 계약 오류가 난다.
실행 간 모델 출력이 달라질 수 있으므로 16건 원 실행의 정확한 원인이라고 단정하지 않는다.

이 기록은 정확도 평가나 32개 전체 흐름의 품질 점수가 아니다. 정답이 확정된
validation/test 케이스와 반복 실행이 아직 없다. ARM 로컬과 아래 x86 EC2 결과도
하드웨어가 달라 직접적인 전후 성능 비교로 사용할 수 없다.

## x86 비공개 EC2에서 수행한 성능 실험

동일한 x86 probe 이미지와 같은 합성 병원 예약 입력(765 입력 토큰, 56 출력 토큰),
`m7i-flex.large`, PyTorch 1 CPU 스레드에서 콜드 부팅 첫 요청을 비교했다.
애플리케이션 준비 시간과 `/chat` 응답 시간은 별도 계측했다.

| 시작 방식 | 준비 시간 | 첫 `/chat` | 준비+첫 `/chat` |
| --- | ---: | ---: | ---: |
| 워밍업 없음, 1회 | 1.52초 | 60.542초 | 약 62.06초 |
| 1토큰 워밍업, 2회 | 32.24초 | 39.843초 / 41.271초 | 약 72.08초 / 73.51초 |

워밍업은 사용자가 요청을 보낸 뒤 기다리는 시간을 줄였지만 계산을 시작 단계로
이동시켰다. 관측한 총 소요 시간은 오히려 길었으며 표본도 적어 총 성능 개선으로
주장할 수 없다. 따라서 `HF_WARMUP_ON_STARTUP` 기본값은 `false`다.

같은 인스턴스의 별도 2 CPU 스레드 probe에서는 첫 요청 65.238초,
후속 요청 46.014초였다. 1 CPU 스레드 후속 요청 41.331초와 40.523초보다
빠르지 않았다. 실행 순서와 캐시 효과가 통제되지 않았으므로 스레드 수 변경을
최적화 결과로 채택하지 않았다. `HF_CPU_THREADS`는 후속 통제 실험용 선택 설정이다.

다음 성능 개선 후보는 양자화된 런타임의 동일 입력 반복 측정이다. 품질 검증 전에
속도만으로 런타임을 교체하지 않는다.

독립된 검증·구조·문서 검토에서 기존 결과 파일에는 불일치 필드 이름만 있어 원인을

`ai_assisted_unreviewed`이며 사람의 정답 합의가 아니다.

초안과 불일치한 필드 21개 중 9개는 초안에 값이 있지만 모델이 `null`을 반환했다.
6개는 같은 의미일 가능성이 있는 표현 차이, 1개는 숫자와 단위의 형식 차이
후보이며, 어느 것도 자동으로 정답에 추가하지 않는다. 3개는 발화에 없는
`오후`를 시간에 붙였고, 1개는 `5시`를 `15:00`으로 잘못 바꿨다. 나머지 1개는
환불 가능 여부를 묻는 발화를 희망 처리 `refund`로 읽었지만 초안은 `null`로 둔
사례로, 의미 판단과 초안 검토가 함께 필요하다. 주민등록 등본의 계약 실패는 두
시도 모두 `provide_details`를 선택하면서 이번 턴 필드를 전부 `null`로 둔
행동·필드 모순이었다.

이 재실행은 첫 16건 실행의 출력 원문을 복원한 것이 아니다. 동일 설정에서 관찰한
추가 표본이며, 개별 오류의 반복률이나 모델 정확도를 주장할 수 없다. 다음 단계는
표현·형식 후보와 환불 의사 해석을 사람이 검토하고, 명백한 시간 오류와 누락을
분리해 수정안을 실험한 뒤 검수된 데이터로 재평가하는 것이다.

### 계약 실패 5건의 재현 진단

같은 Q5 모델·이미지·서버 설정에서 실패 사례 `C06`, `C08`, `C12`, `C16`, `C20`만
다시 실행했다. [별도 결과 JSON](exploratory-q5-ai-candidate-failure-codes-2026-10-10.json)에
입력 파일·모델·이미지 해시, 선택한 사례 ID, 마지막 검증 오류의 분류만 남겼다.
다섯 건 모두 재실행에서도 계약에 실패했고, 마지막 오류는 모두
`action_missing_required_field`였다. 이는 JSON 키가 빠졌다는 뜻이 아니라,
모델이 선택한 행동에 필요한 **이번 턴 필드 값**이 없다는 검증기 분류다.
원 출력과 각 시도의 오류 메시지는 저장하지 않았으므로 어느 행동·필드가
문제였는지, 첫 실행에서도 동일한 이유였는지는 확인할 수 없다.

초안의 `user_action`과 달랐던 11건도 사람 검수를 거치지 않은 라벨과의
불일치일 뿐이다. 출력 행동 자체나 발화별 의미 판단을 저장하지 않았기에
11건을 모델 오답으로 셀 수 없다. 이 재실행과 초안 비교는 모두 개발 진단이며
정확도 개선율의 분모·분자에 포함하지 않는다.

### 업무 범위 밖 발화 지시문 비교

실패 5건(`C06`, `C08`, `C12`, `C16`, `C20`)과 각 업무의 정보 제공 대조군
5건(`C05`, `C07`, `C11`, `C15`, `C19`)을 로컬 Q5에서 기본 지시와 추가
지시로 한 번씩 비교했다. 사례마다 실행 순서를 번갈아 배치했다. 추가 지시는
업무 밖 발화를 현재 업무 필드로 옮기지 말고, 허용된 경우 `unknown`과 null
필드를 선택하라는 내용이다. [실험 JSON](exploratory-q5-out-of-scope-instruction-2026-10-10.json)에
두 조건의 마지막 검증 오류 분류, 초안과 다른 필드 이름, 토큰·시간, 입력·모델·이미지
해시를 기록했다. 발화와 출력 원문은 저장하지 않았다.

- 업무 밖 5건의 출력 계약: 기본 **0/5**, 추가 지시 **3/5**. `C06`, `C08`,
  `C12`는 추가 지시에서 계약을 통과하고 미검수 초안 라벨과도 일치했다.
  `C16`, `C20`은 두 조건 모두 이번 턴 필드 값 부족으로 실패했다.
- 정보 제공 대조군 5건의 출력 계약: 양쪽 모두 **5/5**. 초안과 다른 필드
  이름도 각 사례에서 두 조건이 동일했다. 이는 그 필드의 의미 정확성을
  확인한 결과는 아니다.

이 작은 비교는 이미 모델에 노출된 AI 미검수 개발 사례를 사용했다. 실행당 한
표본이고 프롬프트 길이·캐시가 달라 전체 정확도나 속도 개선율로 해석할 수 없다.
실패 2건이 남았고 사람 검수 정답도 없으므로 추가 지시는 서비스에 적용하지 않았다.

### 공통 실패 형태와 행동·필드 제약 실험

공통 실패 `H14`, `H16`, `H18`, `H19`, `H20`을 두 모델에서 한 번씩 다시 실행하고
출력값 대신 허용된 행동 코드와 값이 채워진 필드 **이름만** 기록했다
([Q5](exploratory-q5-common-failure-shapes-2026-11-03.json),
[Q4](exploratory-q4-common-failure-shapes-2026-11-03.json)). 두 모델 모두
`H14`, `H16`, `H18`, `H19`에서 `provide_details`와 빈 이번 턴 필드를 두 번
연속 반환했다. `H20`에서는 `provide_details`와 함께 `change_field=request_topic`을
두 번 반환했다. 이는 JSON 파싱 실패가 아니라 행동·필드 관계의 계약 위반이다.

이 관계를 제약하는 실험용 JSON 스키마를 라이브 업무 계약에서 생성해, 실패 5건과
같은 범주의 정보 제공 대조군 `H13`, `H15`, `H17`에 적용했다. 같은 모델 파일·서버
이미지·입력 문서 해시·CPU·스레드·요청 설정을 유지했다. pinned `llama.cpp` 이미지에서
`response_format.type=json_schema`로 보낸 Q4 `H14` 한 건은 여전히 계약에
실패했다([기록](exploratory-q4-constrained-h14-smoke-2026-11-03.json)).
`response_format.type=json_object`와 `schema`를 함께 보낸 조건은 다음과 같았다.

| 8건 탐색 비교 | Q5 기본 → 스키마 | Q4 기본 → 스키마 |
| --- | ---: | ---: |
| 출력 계약 통과 | 3/8 → 8/8 | 3/8 → 8/8 |
| 미확정 라벨 초안 전체 일치 | 0/8 → 3/8 | 0/8 → 1/8 |

스키마 조건은 두 모델 모두 `H19`와 `H20`에서 라벨 초안과 행동·필드가 불일치했다.

계약 통과를 늘리면서 다른 행동을 선택하게 할 수 있음을 보여준다. 대조군 3건은
기본·스키마 조건 모두 계약을 통과했지만 초안과의 필드 불일치는 유지됐다.

[Q4 스키마](exploratory-q4-workflow-schema-8-2026-11-03.json),
